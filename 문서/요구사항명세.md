# E2E 검증 도구 요구사항 명세.

협의는 2026-09-24에 시작했고 이 초안은 2026-09-25에 정리했다. 이 문서는 첫 적용 대상의 현재 소스 확인과 담당 세션 회신 `msg_17b9efe69324`에 기반한다. 제안 사항은 사용자 승인이나 구현 완료를 뜻하지 않는다.

## 1. 목적과 범위.

사람과 AI가 같은 검증 결과를 사용한다. 반복 검사는 코드가 실행하고 AI는 필요한 실패 증거만 읽는다. 사람은 검사 목적→사전 조건/행동→기대 결과→실제 관측→판정→증거→미검증 범위를 한국어로 이해하고 기준 변경을 판단한다. 원본 로그만 나열한 화면으로 대체하지 않는다.

첫 적용은 `C:/dev/atelier-note`의 고객·상담·기본 신체 치수·상품·자유 품목·세트·견적 초안·직원 인증이다. 공통 엔진을 재사용할 수 있게 하되 두 번째 프로젝트가 생기기 전에는 범용 플러그인 시장이나 모든 프레임워크 자동 탐지를 만들지 않는다.

Windows 데스크톱 앱, 운영 배포, 실자료 이관, 실제 계정 비밀번호 변경, 원격 DB, 유료 AI·외부 서비스 호출, 자동 코드 수정은 첫 버전 범위에 포함하지 않는다. 업무 기능의 정답을 코드만 보고 자동 확정하는 기능도 제공하지 않는다. 재고관리는 아틀리에 업무의 후속 기능이 아니라 사용자 요구로 제외된 범위다.

담당 세션이 전달한 사용자 경계에 따라 열린 브라우저·네이티브 앱·Pen 편집기를 조작하지 않는다. 향후 승인된 격리 헤드리스 시험은 별도이며 이번 협의에서는 실행하지 않는다.

## 2. 현재 확인한 대상 프로젝트.

아래 상태는 파일 확인 결과다. 이번 협의에서 해당 테스트를 실행해 통과를 재확인한 것은 아니다.

| 구분 | 현재 상태 | 설계에 미치는 영향 |

| 앱 구성 | Next.js 프론트, NestJS 기반 Worker 백엔드, Better Auth·Drizzle, 로컬 PostgreSQL17. | 브라우저·API·DB의 실제 연결을 한 실행의 증거로 묶는다. |
| 개발 주소 | 프론트3000, 백엔드4000. 로컬 DB는 `respiro_local`,5432. | 기존 개발 서버·실자료 환경을 테스트 전용으로 오인하지 않는다. |
| 빠른 검사 | `npm run verify:quick`의 서식·타입·러너·단위 검사. | 최초 연결 대상으로 재사용한다. |
| 기존 전체 검사 | `npm run verify`는 준비·정적·단위/통합·빌드·브라우저 검사를 순차 실행한다. | 현재 DB 전환을 반영한 새 실행 계획이 필요하다. |
| 기존 업무 브라우저 검사 | 고객·견적·상품·세트는 공유 로컬 D1 fixture와 고정3000 주소를 사용한다. | PostgreSQL 앱에 그대로 실행하지 못하도록 차단한다. |
| 직원 화면 검사 | `staff-workflow.mjs`는 모의 API 화면 검사다. | 실제 인증·DB E2E와 별도 분류한다. |
| PostgreSQL 검사 | `tests/postgres/`에 Docker 기반 격리 DB·인증·업무·원자성·이관 검사가 있다. | 기존 시험을 재사용하고 브라우저 연결 공백을 채운다. |
| 기존 보고서 | 실행별 `report.json`, `summary.txt`, 단계 로그. 최상위 종료코드는 기록하지 않는다. | 과거 JSON의 통과 주장과 실제 프로세스 종료 증거를 구분한다. |
| 검증 화면 초안 | `scripts/검증-결과.mjs`, `scripts/검증-서버.mjs`, `scripts/검증화면/`은 미완성·미커밋 상태다. | 설계 참고 자료이며 그대로 완료 기능으로 이전하지 않는다. |
| 디자인 | 설계29.14절과 라이트 시안 HTML이 최신 대표 화면 기준이다. | 실제 앱의 전면 적용·전체 화면 기준 이미지 승인은 미완료다. |

원본 근거는 9절에 둔다. 인수인계·설계서의 아래쪽에는 과거 네이비 디자인과 D1 실행 설명이 함께 남아 있으므로 최신 상단과 후속 개정 절을 우선한다.

## 3. 필수 기능.

우선순위 P0는 기본 도구 도입에 필요한 기능이다. P1은 실제 업무 검증을 완성하는 기능이며 P2는 후속 확장이다. 첫 시연 M0는 P0의 일부다. 기존 PostgreSQL 검사 연결까지 끝난 M1과, 실제 브라우저 대표 흐름을 연결한 M2를 구분하며 M0를 P0 전체 완료라고 부르지 않는다.

|---|---|---|---|
| 공통-01 | P0 | 프로젝트·검사 계획 등록과 사전 점검. | 실행 없이 대상·명령·DB 영향·미실행 범위를 보여주고 설정 오류를 설명한다. |
| 공통-02 | P0 | 하나의 엔진을 CLI와 로컬 stdio MCP로 호출. | 양쪽에서 같은 실행번호의 동일한 판정과 증거를 조회한다. |
| 공통-03 | P0 | 비동기 실행·조회·명시적 취소·중복 실행 방지. | 시작 요청의 반복 전송으로 실행이 늘지 않으며 다른 세션의 프로세스를 종료하지 않는다. |

## 4. 첫 업무 시나리오.

각 시나리오는 업무 요구사항→테스트 ID→실행 결과→증거로 연결한다. 아래는 기존 구현에 대한 검사 범위이며 미구현 기능을 섞지 않는다.

| ID | 흐름 | 정상 조건 | 거절·실패 조건 | 주요 근거 |
|---|---|---|---|---|
| 업무-01 | 로그인과 직원 상태. | 허용된 가상 계정 로그인, 역할에 맞는 화면/API 접근. | 미승인·비활성·세션 만료·강제 비밀번호 변경 상태를 우회할 수 없음. 초기화 뒤 이전 세션 차단. | `tests/postgres/auth.test.ts`, `staff.test.ts`, `http.test.ts`. |
| 업무-02 | 고객→상담→기본 신체 치수. | 가상 고객 생성·수정·재조회, 상담/치수 이력과 보관 상태 유지. 치수0.1cm와 내부 정수 표현, 빈 값과0의 구분. | 연락처 정규화 중복, 보관 고객의 하위 변경, 잘못된 입력, 버전 충돌, 미저장 이동, 응답 유실 재시도에서 중복/입력 유실 방지. | `tests/e2e/first-workflow.mjs`, `tests/postgres/customers.test.ts`, `tests/unit/contracts.test.ts`. |
| 업무-03 | 상품·자유 품목·세트→견적 초안. | 선택 품목과 구성·금액·할인·정수 배분 합계가 저장과 재조회에서 일치. | 50품목 경계, 안전 정수 초과, 빈 견적·위조 합계·중첩 세트 거절, 숨긴 상품, 버전 충돌, 중복 제출, 원본 상품 변경 뒤 견적 사본 보존. | 기존 상품·세트·견적 E2E, `tests/postgres/quotes-products.test.ts`. |

앱은 현재 단일 매장용이다. 다중 업체 격리를 구현된 필수 조건으로 가정하지 않는다. 역할은 `owner`, `developer`, `staff`이며 재무정보의 owner 전용 정책은 후속 구현 목표와 현재 구현을 나누어 등록한다.

주문·수납·매출·확장 상담·사진 AI·Pinterest 자동 선별·원본 채촌 양식의 펜 필기는 미래 요구 목록으로 남긴다. 현재 기본 치수 입력과 원본 양식/펜 기능을 혼동하지 않는다.

## 5. 디자인 검증 기준.

- 최신 대표 기준은 `docs/레스피로-라이트-시안.html`과 설계29.14절이다. 배경 `#F8F9F6`, 본문 `#222C29`, 설명 `#616B65`, 버튼 `#28483D`, 보조 배경 `#E9EEEA`를 해당 역할에 매핑한다. 모든 요소를 이 색만 쓰도록 강제하지 않는다.
- 한글 본문 고딕·영문 매장명 명조, 사진과 여백의 균형은 대표 방향이다. 전체 화면의 서체 크기·간격 수치·허용 오차는 아직 확정되지 않았으므로 임의의 합격 기준을 만들지 않는다.
- 공통 반응형 검증 약속은 설계24.2절의1440/1024/768/390px다.1280/320px는 대표 시안 추가 확인 이력이며 전 앱 확정 기준으로 확대하지 않는다. 실제 업무 우선순위는 태블릿과 데스크톱이며 긴 이름·빈 목록·API 실패·키보드 상태를 함께 확인한다. 실기기 펜·촬영·성능 검증을 브라우저 에뮬레이션으로 대체했다고 보고하지 않는다.
- 효과3단계는 설계 목표이고 최신 대표 HTML의 효과 on/off는 예시 구현이다. 무음·동작 줄이기를 확인하되 목표와 현재 구현을 구분한다. 미커밋 Pen 작업본과 이전 네이비19보드는 전체 화면의 골든 이미지로 채택하지 않는다.
- 화면 기준은 `draft`·`accepted`·`implemented`·`verified`를 구분한다. 시안 수용을 앱 적용 완료나 전체 화면 승인으로 올리지 않는다.
- 기준 스크린샷에는 화면·상태·가상자료·브라우저·OS·폰트·viewport·기준 파일 해시를 묶는다. 동적 요소·애니메이션은 명시한 정책으로 고정한다.
- AI가 실패를 해결하려고 기대값·허용 오차·기준 이미지를 자동 변경하지 못한다. 변경은 사람에게 전후 차이를 제시한다.
- 접근성 자동 검사·기하학적 검사·스크린샷 차이·사람의 미적 판단을 별도 분류한다. 스캐너 통과를 전체 접근성 인증으로 표시하지 않는다.

## 6. 안전한 검사와 증거.

DB 쓰기 계획에는 엔진·로컬/원격·격리 여부·DB 이름·테이블·조건·동작·예상 영향·정리 방법을 포함한다. 테스트 내부의 마이그레이션·가상자료 입력·삭제도 쓰기에 포함한다. 현재 대화의 사용자 확인을 근거로 범위를 고정하며 이전 세션의 승인 문구를 실행 권한으로 가져오지 않는다.

`respiro_local`과 기존 D1은 새 도구의 자동 쓰기 대상으로 등록하지 않는다. 전용 테스트 컨테이너와 서버를 만들고 실행별 소유권을 기록한다. 현재 PG fixture는 공통 purpose label만 있고 새 도구 runId와 연결돼 있지 않으므로 해당 연결을 선행한다. Node 종료만으로 Docker 자원 정리를 확인했다고 처리하지 않는다. 정리 실패는 경고 없이 버리지 않고 잔여 자원 ID와 다음 확인 절차를 남긴다. 승인 밖의 DB 청소·잠금 강제 해제·다른 서버 종료는 제공하지 않는다.

기존 서버 명령은 실제 `backend/.env.postgres.local`과 `backend/.env.local`을 읽으며 포트도 고정한다. 가상환경에서는 이 경로로 되돌아가는 기본 동작 없이 명시적인 시험 설정과 포트를 사용해야 한다. 기존 명령에 환경변수만 덧붙여 격리됐다고 판단하지 않는다. `history`는 대상 자료를 읽기만 하며, `quick`은 DB 쓰기는 없지만 보고서·로그·임시 파일·캐시를 쓸 수 있다.

API 요청·응답은 허용한 필드와 가상자료만 공개한다. 쿠키·인증 헤더·연결 문자열·비밀번호·실제 고객 정보·원가표는 요약과 공개 증거에서 제외한다. 원본 로그와 trace는 민감할 수 있으므로 로컬 제한 자료로 보관하고 MCP/조회 화면에서 자동 노출하지 않는다. 캡처와 trace의 픽셀·DOM에 민감정보가 포함될 수 있어 텍스트 정규식만으로 안전하다고 판정하지 않는다.

## 7. 첫 도입 완료 기준.

1. 같은 실행번호를 CLI·MCP·사람 화면에서 조회하면 상태·집계·미검증 범위가 같다.
2. 기존 과거 D1 결과·직원 모의 화면 결과·신규 격리 PostgreSQL 결과가 섞이지 않는다.
3. DB 대상 불일치·승인 없음·Docker/브라우저 준비 실패·기준 없음이 분명하게 표시된다.
4. 첫 도입에서는 격리 PostgreSQL 실제 브라우저 대표1흐름과 실행에 귀속된 실패 증거를 확보한다. 이후 업무-01~04를 넓혀 전체 프로필을 완성한다.
5. 권한 우회, 잘못된 합계, 모바일 넘침을 시험용 대상에 의도적으로 넣었을 때 해당 검사가 실패한다. 결함 제거 후 통과한다.
6. 소스 변경, timeout, spawn 실패, 보고서 저장 실패, 취소, 정리 실패에서 거짓 통과가 없다.
7. CLI/MCP 중복 호출·연결 해제·프로세스 재시작을 시험하고 다른 세션의 자원은 유지한다.
8. 가짜 비밀 값·고객 식별값을 넣은 오류와 캡처로 유출 방지를 확인한다. 경로 순회·정션·HTML 삽입도 확인한다.
9. 대표 실패 세 건으로 사람이 원인을 찾는 시간과 AI 입력량을 측정한다. 로그 바이트 감소를 실제 토큰 절감률로 부르지 않는다.

## 8. 구현 전에 확정할 사항.

- M0는 이력 조회·단계 수준의 빠른 검사·CLI/MCP·사람 화면, M1은 구조화 결과와 자원 소유권을 연결한 기존 격리 PostgreSQL 검사, M2는 실제 브라우저 대표1흐름이다. 이후 나머지 업무·디자인으로 확장한다. M0/M1을 현재 업무 전체 검증으로 표시하지 않는다.
- 대상 앱의 연결 주소·시험 전용 설정 경로·구조화 결과 출력과 E2E/기존 PG fixture 변경은 아틀리에 담당 세션이 소유한다. 새 E2E 도구는 실행·보고·증거를 소유한다. 해당 세션은 현재 E2E 준비 전까지 앱 구현을 대기하며 협의만 진행한다.
- DB 검증 실행은 구체적인 격리 대상과 영향 계획을 제시한 뒤 현재 사용자 확인을 받는다. 이번 문서 작성은 실행 승인이 아니다.
- 미확정 디자인 수치와 화면별 기준 이미지는 화면 적용 시점에 정한다. 원격 서비스와 운영 검사는 별도 설계한다.

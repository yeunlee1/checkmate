# Windows 자동 업데이트.

Squirrel로 설치한 Windows 앱은 시작 60초 뒤와 이후 30분마다 GitHub Releases의 최신 정식 버전을 확인한다. 설정의 **앱 업데이트**에서 직접 확인하거나 다운로드된 버전을 재시작해 적용할 수 있다. 개발 실행과 압축만 푼 포장 앱에서는 비활성이다. 예전 설치본에 이 기능이 없으면 기능을 포함한 설치본을 한 번 직접 설치해야 한다.

## 실행과 자료 보호.

Squirrel은 다운로드 과정에서도 설치 폴더를 변경하므로 다운로드 전과 재시작 전 모두 설치본 공통 잠금을 잡고 프로세스를 확인한다. 같은 설치본의 Node·작업 보호·업데이트 프로세스가 살아 있거나 경로를 확인하지 못하면 보류한다. 자료 폴더가 달라도 같은 설치본의 엔진을 보호한다. 새 서비스와 CLI 연결은 잠금이 풀릴 때까지 시작하지 않는다. 실행 중인 검사나 다른 세션을 강제로 종료하지 않는다.

MCP 연결이 남아 있으면 사용하는 클라이언트에서 연결을 정상 종료한다. 검사를 마친 서비스는 기존 유휴 정책에 따라 종료되며 이후 업데이트 확인을 다시 누른다. 내려받은 버전은 다음 앱 시작에서 사용될 수 있으므로 설정 화면의 재시작 버튼만이 적용 시점은 아니다.

네트워크·패키지 오류는 화면에 실패로 표시하고 다시 시도할 수 있다. 앱이 비정상 종료된 경우 기록된 소유 PID의 종료와 설치 프로세스 부재를 모두 확인해야 잠금을 회수한다. 확인이 불가능한 잠금은 자동 삭제하지 않는다. 이 잠금은 실행 이력의 `ownership-unknown` 사람 확인 게이트와 별개이며 과거 판정을 바꾸지 않는다.

앱 파일과 기존 자료 폴더는 분리되어 있다. 이 변경에는 DB 스키마 변경이 없다. 이후 DB 버전을 바꾸는 릴리스는 기존 설계의 사전 백업·사용자 확인·호환성 검사 조건을 별도로 충족해야 한다.

## GitHub Actions와 정식 게시.

`.github/workflows/업데이트배포.yml`은 관련 PR과 수동 실행에서 빌드·회귀·Electron·포장 앱·합성 업데이트를 검사하고 개발 설치 산출물을 보관한다. 수동 실행은 공개 릴리스를 만들지 않는다.

정식 배포는 별도 승인 후 다음 순서로 진행한다.

1. 루트와 세 패키지 및 `package-lock.json`의 버전을 같은 정식 `N.N.N`으로 올리고 관련 검증을 통과한다.
2. `develop → main` PR을 병합 커밋으로 통합한다.
3. 깨끗한 main 소스에서 `vN.N.N` 태그를 게시한다. 워크플로는 태그·버전·main 계보를 검사한다.
4. 빌드 작업에서 서명과 타임스탬프를 검증하고 `RELEASES`의 SHA1·크기·파일명 및 전체 산출물 SHA256을 대조한다.
5. 게시 작업에서 SHA256과 소스를 다시 확인한다. 기존 최신 버전보다 높은 정식 버전만 초안에 전부 업로드한 뒤 최신 공개 릴리스로 전환한다. 실패한 초안은 자동 공개하지 않는다.

공개 피드는 `https://github.com/yeunlee1/checkmate/releases/latest/download`로 고정된다. 저장소를 비공개로 바꾸면 현재 익명 업데이트 방식도 변경해야 한다. 게시 자격은 해당 작업의 `GITHUB_TOKEN`에만 `contents: write`를 부여한다. 실행 파일명은 기존 설치 호환성을 위해 `CheckMate-개발설치.exe`를 유지하며 정식 여부는 태그와 서명 검사로 구분한다.

## 외부 서명 설정.

정식 태그 빌드에는 저장소 Actions 비밀 값 `CHECKMATE_SIGN_PFX_BASE64`와 `CHECKMATE_SIGN_PFX_PASSWORD`가 필요하다. 공개적으로 신뢰되는 코드 서명 인증서여야 하며 자체 서명 인증서는 정식 게시 조건을 충족하지 않는다. 인증서와 비밀번호를 소스·이슈·대화에 붙여 넣지 않는다.

워크플로는 임시 PFX를 현재 사용자 인증서 저장소로 가져온 뒤 삭제하고, 인증서 지문으로 앱과 Squirrel 설치본을 서명한다. 비밀번호를 서명 명령줄에 전달하지 않는다. 작업 종료 시 가져온 서명 인증서를 제거한다. 인증서가 없거나 서명·타임스탬프가 유효하지 않으면 태그 배포가 실패한다. 하드웨어 키나 원격 서명 서비스를 사용하는 인증서는 제공자의 러너 연동을 별도 구성해야 하며 현재 PFX 경로와 같은 것으로 취급하지 않는다.

이번 기능 구현과 develop 병합은 인증서 발급·비밀 값 등록·main 릴리스·공개 태그 게시·기존 설치본 교체를 수행하지 않는다. 합성 로컬 피드 수용은 공개 GitHub 피드 및 정식 서명 배포 검증과 구분한다.

근거는 [Electron 업데이트](https://www.electronjs.org/docs/latest/tutorial/updates), [autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater), [Forge Windows 서명](https://www.electronforge.io/guides/code-signing/code-signing-windows), [GitHub 최신 릴리스 링크](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)다.

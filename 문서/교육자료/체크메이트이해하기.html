복잡한 지도를 보기 전에, 검사 요청 하나를 따라가 봅시다. 사람과 AI가 들어오는 입구부터 결과를 믿을 수 있는 조건까지. 마지막에는 실제 코드를 읽을 차례입니다.

첫 번째 읽기그림으로 전체 흐름 이해
두 번째 읽기코드 펼치고 역할 확인
마지막 확인직접 설명하고 예제 실행
첫 장면 시작하기 →필요한 코드부터 찾기
코드가 낯설다면 · 읽는 데 필요한 표기 여섯 가지.
  • import는 다른 파일의 도구를 가져옵니다. 가져오기 관계만으로 실행 순서를 알 수는 없습니다.
  • export는 다른 파일에서도 쓸 수 있게 공개합니다.
  • function은 입력을 받아 일을 하는 단위입니다. 괄호 안은 입력, return 뒤는 돌려주는 값입니다.
  • class는 함께 쓰는 상태와 동작을 묶습니다. 예를 들어 RunService는 실행 큐와 시작·취소 동작을 관리합니다.
  • async / await는 기다려야 하는 작업을 다룹니다. 기다린다는 표기 자체가 검사 통과를 뜻하지는 않습니다.
  • throw는 현재 작업을 오류로 멈춥니다. 화면에 보이는 오류 코드는 다음 행동을 고르는 단서입니다.

각 코드는 “받는 값 → 막는 조건 → 호출하는 다음 함수 → 돌려주는 값” 순서로 읽어 보세요.

SCENE 01 · 역할

누가 판단하고, 누가 실행할까요?

체크메이트는 AI의 머리가 아닙니다. 실제 검사를 실행하고 기록하는 도구입니다. 검사 대상 프로그램도 체크메이트와 별개입니다.

사람

무엇을 검사할지 정하고 실행 범위와 기준을 확인합니다.

AI

검사를 작성하고 도구를 호출합니다. 결과를 읽고 코드 수정을 돕습니다.

체크메이트

승인된 검사를 실제로 실행하고 결과와 증거를 저장합니다.

검사 대상 프로그램

내가 개발하는 웹앱·백엔드와 그 프로젝트에 연결한 검사 코드.

이 그림은 책임의 구분입니다. 사람의 승인도 검사 기준의 정확성을 자동으로 보장하지는 않습니다.

비유 · 시험 감독과 답안지.AI가 시험 문제와 수정을 돕고, 체크메이트가 시험을 진행해 답안과 근거를 남깁니다. 시험에 넣지 않은 과목까지 합격했다고 말할 수는 없습니다.

체크메이트 자체는 LLM API를 호출하지 않습니다. 사용 중인 Codex·Claude Code 같은 외부 AI가 MCP나 CLI를 사용합니다. 사용량과 요금 조건은 그 AI 서비스의 계정을 따릅니다.

SCENE 02 · 연결

입구는 셋, 검사 서비스는 같습니다.

화면을 누르든 터미널에서 명령을 쓰든, AI가 도구를 부르든 같은 자료 폴더의 로컬 서비스에 도달합니다.

  1. 데스크톱 화면버튼으로 요청
  2. 공통 클라이언트로컬 서비스에 전달
  3. 제품 서비스입력·권한·작업 조건 확인
  4. 실행과 기록검사 수행·결과 조회

React 화면은 preload가 공개한 통로를 사용합니다. Electron main이 요청자를 확인한 뒤 callService로 전달합니다.

App.start → window.checkmate.request → IPC → callService → ProductService.handle

로컬 서비스는 인터넷에 배포한 서버가 아닙니다. Windows에서는 이름 있는 파이프, 다른 지원 환경에서는 로컬 소켓으로 연결합니다. 데스크톱 창을 닫는 것과 실행 중인 검사 서비스의 종료는 구분됩니다.

같은 컴퓨터여도 앱과 MCP의 자료 경로가 다르면 다른 저장소를 보게 됩니다. AI에게 프로젝트가 보이지 않을 때는 먼저 --data-dir와 앱 설정의 자료 위치를 맞춰 봅니다.

SCENE 03 · 실행 전 약속

정의, 계획, 승인은 서로 다릅니다.

“주문 저장을 검사하자”는 말만으로는 실행할 수 없습니다. 무엇이 맞는지, 어떤 코드로 확인할지, 이번에는 어디까지 실행할지 연결해야 합니다.

프로젝트가 제공하는 세 파일

  1. 요구사항.json

    무엇이 되어야 하나요? 예를 들어 저장한 주문을 다시 읽을 수 있어야 합니다.

  2. 검사항목.json

    무엇과 연결되나요? 기대값·필수 여부·실행 명령·관련 코드를 정합니다.

  3. 프로젝트.json

    무엇을 실행하나요? Node 진입점과 인자·환경·검사 묶음을 정합니다.

실행 전에 만드는 약속

  1. 묶음을 선택합니다.

    이번 검사 목록과 필요한 명령이 선택됩니다.

  2. 계획을 확인합니다.

    현재 소스, 정의, 명령과 환경을 지문으로 묶습니다.

  3. 사람이 승인합니다.

    그 계획의 정확한 범위를 확인한 기록을 남깁니다.

비유 · 서명한 주문서.음식 이름이 같아도 재료와 수량을 바꾸면 다른 주문입니다. 소스나 검사 기준이 바뀌면 과거의 승인을 그대로 쓸 수 있다고 가정하지 않습니다.

소스가 바뀌면 새 계획을 확인합니다. 세 정의 파일이 바뀌면 원본을 비교하고 필요한 기준 활성화도 합니다. 비교 화면은 검사 ID의 변화만 보여 주므로 요구사항·명령의 변화는 원본 JSON 또는 Git 차이에서 따로 읽습니다.

export async function readProjectSource(root: string): Promise<ProjectSnapshot> {
  const realPath = await checkedProjectRoot(root);
  const before = await readCatalog(realPath);
  const sourceHash = await fingerprintSource(realPath);
  const after = await readCatalog(realPath);
  if (before.contentHash !== after.contentHash) {
    throw new ProjectSourceError('source-changed', '프로젝트 원본이 읽는 동안 변경되었습니다.');
  }
  return { realPath, source: before.source, contentHash: before.contentHash, sourceHash };
}

SCENE 04 · 한 번의 실행

접수에서 최종 기록까지 따라가 봅시다.

버튼이 성공 응답을 받았다는 것은 시작 요청이 받아들여졌다는 뜻입니다. 검사가 끝났다는 뜻은 아닙니다.

export function assessResult(result: RunResult): Assessment {
  if (result.state === 'queued' || result.state === 'running') {
    return { verdict: null, reasons: ['run-not-finished'] };
  }
  if (result.origin === 'imported') return { verdict: 'unknown', reasons: ['imported-evidence'] };

  const reasons: string[] = [];
  const cases = new Map(result.cases.map((item) => [item.testId, item]));
  const observedFailure = result.cases.some((item) => item.status === 'failed');
  if (observedFailure) reasons.push('check-failed');
  const workerFailed = result.state === 'finished' && result.workerExitCode !== null && result.workerExitCode !== 0;
  if (workerFailed) reasons.push('worker-failed');
  if (!result.finalized) reasons.push('result-not-finalized');
  if (result.state !== 'finished') reasons.push(`run-${result.state}`);
  if (result.requiredChecks.length === 0) reasons.push('required-checks-empty');
  const missing = result.requiredChecks.filter((id) => cases.get(id)?.status !== 'passed');
  if (missing.length > 0) reasons.push('required-checks-incomplete');
  if (result.workerExitCode === null) reasons.push('exit-unconfirmed');
  if (result.planHash === null) reasons.push('plan-unconfirmed');
  if (result.sourceBefore === null || result.sourceAfter === null) reasons.push('source-unconfirmed');
  else if (result.sourceBefore !== result.sourceAfter) reasons.push('source-changed');
  if (result.environmentVerified !== true) reasons.push('environment-unconfirmed');
  if (result.evidenceVerified !== true) reasons.push('evidence-unconfirmed');
  if (result.cleanupVerified !== true) reasons.push('cleanup-unconfirmed');

  if (observedFailure || workerFailed) {
    return { verdict: 'failed', reasons };
  }
  if (result.state === 'blocked' || result.state === 'cancelled') return { verdict: 'incomplete', reasons };
  if (!result.finalized || result.state === 'unverifiable' || reasons.some((reason) => reason.endsWith('-unconfirmed')) ||
    result.requiredChecks.some((id) => cases.get(id)?.status === 'unknown')) {
    return { verdict: 'unknown', reasons };
  }
  return { verdict: reasons.length === 0 ? 'passed' : 'incomplete', reasons };
}

SCENE 06 · 수정과 재검사

어디를 고쳐야 하는지부터 나눕니다.

“검사가 실패했다”는 사실과 “체크메이트가 고장 났다”는 결론은 다릅니다. 기대값, 실제 관측, 증거를 읽고 문제의 위치를 좁힙니다.

  1. 이번 실행을 특정합니다.

    프로젝트·검사 묶음·실행 ID·최종 확정 여부를 확인합니다.

  2. 요약에서 필요한 근거로 내려갑니다.

    실패 검사, repair-bundle, 관련 증거를 읽습니다. 모든 로그를 한꺼번에 AI에 보내는 방식보다 필요한 구간을 조회합니다.

  3. 대상 프로그램 문제인지 도구 문제인지 구분합니다.

    잘못된 저장값은 업무 코드, 기대값 자체가 틀렸다면 검사 기준, 결과 전달이 깨졌다면 리포터나 연결 경로를 확인합니다.

  4. 바뀐 소스로 새 계획을 확인합니다.

    필요한 기준 활성화와 승인을 거친 뒤 다시 실행합니다. 실패를 없애려고 검사를 지우거나 기대값을 낮추지 않습니다.

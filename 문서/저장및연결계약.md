# 체크메이트 저장 및 연결 계약.

[구현 기준 설계](구현기준설계.md)의 상세 계약이다. 아래 테이블과 예시는 설계이며 DB 생성·마이그레이션을 실행하지 않는다. 첫 외부 계약 버전은1, 저장 스키마 버전은1로 시작한다.

## 1. 원본과 버전.

프로젝트 Git의 `checkmate/프로젝트.json`, `요구사항.json`, `검사항목.json`, `기준/`, 테스트 코드가 등록 원본이다. 초기 등록은 사람이 선택한 실제 경로와 원격 식별자를 확인한다. 프로젝트 UUID는 경로 이동이나 작업 브랜치가 달라져도 유지하고 작업 폴더는 별도 workspace ID로 구분한다. 파일을 다른 프로젝트로 복사해 ID가 충돌하면 자동 병합하지 않는다.

검사 원본에는 안정된 ID, 요구사항 ID, 제목, 목적, 전제, 실행 명령 ID, 결과 변환기 ID, 필수 여부, 범위·역할·기준 참조, 코드 경로가 있다. 프로필은 실행할 검사 ID·순서·시간 한도·자원·허용 쓰기 범위를 명시한다. 절대 경로와 비밀 값은 원본에 넣지 않는다. 실행 파일·인자 등록은 프로젝트 신뢰를 확인한 후 별도 검토한다.

동기화는 파일 읽기 → 계약 검증 → 이전 버전과 차이 → 활성 기준 변경 확인 → 새 카탈로그 스냅샷 추가 → 프로젝트의 활성 버전 전환 순서다. 불완전한 파일을 부분 적용하지 않는다. AI 후보는 후보 상태로 보관하고 활성 원본을 몰래 바꾸지 않는다. 파일 버전과 DB의 해시가 다르면 `catalog-stale`로 실행을 차단한다. GUI 편집도 원본 파일 변경안을 만들고 동일한 경로로 반영한다.

실행은 Git HEAD만 기록하지 않는다. 포함할 소스·검사·기준·설정 파일의 정렬된 상대 경로와 바이트 해시, 잠금 파일·도구 버전·어댑터 버전으로 지문을 만든다. 수정 중인 파일과 허용한 미추적 소스도 포함한다. `.git`, `node_modules`, `.runtime`, 증거, 비밀 파일은 제외하고 제외 규칙도 지문에 넣는다. 실제 서버가 로드한 build ID와 환경 ID는 별도로 수집한다. 같은 HEAD만으로 같은 실행 환경이라고 판정하지 않는다.

현재 제외 규칙 버전은 2다. 폴더는 `.git`, `node_modules`, `.runtime`, `dist`, `out`, `coverage`, `.vite`, `.next`, `.build`, `.open-next`, `.codegraph`, `.wrangler`, `.local`을 제외한다. 파일은 `.env`, `.env.*`, `.dev.vars`, `.dev.vars.*`, `*.pem`, `*.key`를 제외한다. 경로 이름 비교는 대소문자를 구분하지 않으며 이 위치의 파일은 읽지 않는다. 제외 위치의 명령 진입점은 등록 단계에서 거절한다. 일반 소스와 `next.config.ts` 같은 설정, 검사 원본은 계속 지문에 포함한다. 제외 규칙 변경은 소스 지문을 바꾸므로 이전 계획을 다시 확인하고 승인해야 한다. 이 규칙은 임의의 비밀 파일을 자동 탐지하거나 명령의 간접 파일 읽기를 격리하는 기능이 아니다.

## 2. SQLite 모델.

ID는 UUID 문자열, 시간은 UTC ISO8601, 해시는 소문자 SHA256, boolean은0/1이다. 필수 열은 NOT NULL, JSON 열은 `json_valid`, 상태는 CHECK 제약으로 제한한다. FK는 모든 연결에서 활성화하고 이력 연결은 기본 `ON DELETE RESTRICT`다. 아래 `PK`, `FK`, `UQ`는 기본키·외래키·고유 제약이다.

| 테이블 | 주요 열과 제약 |
|---|---|
| schema_migrations. | version PK, checksum, applied_at, app_version. 적용 이력은 변경하지 않는다. |
| projects. | id PK, name, repository_identity, active_catalog_id FK nullable, created_at, archived_at nullable. |
| workspaces. | id PK, project_id FK, real_path UQ, path_fingerprint, created_at. Windows 경로 대소문자·정션을 정규화한다. |
| catalogs. | id PK, project_id FK, content_hash, source_json, created_at. UQ(project_id, content_hash). 불변 스냅샷. |
| definitions. | catalog_id FK, kind, definition_id, content_json. PK(catalog_id, kind, definition_id). kind는 requirement/check/baseline/profile. |
| requirement_checks. | catalog_id, requirement_id, check_id, required. PK 세 ID. 같은 카탈로그의 requirement/check 정의를 복합 FK로 연결한다. |
| plans. | id PK, workspace_id FK, catalog_id FK, fingerprint, plan_json, source_hash, created_at. 동일 지문은 재사용할 수 있고 승인 대상은 이 불변 스냅샷이다. |
| approvals. | id PK, plan_id FK nullable, scope_hash, scope_json, evidence_kind, evidence_ref, granted_at, expires_at nullable, revoked_at nullable. 비밀 값과 전체 대화를 저장하지 않는다. |
| runs. | id PK, workspace_id FK, plan_id FK, parent_run_id FK nullable, origin, state, verdict nullable, phase, worker_exit_code nullable, started_at, finished_at nullable, finalized_at nullable, summary_json. |
| requests. | workspace_id FK, request_id, request_hash, run_id FK. PK(workspace_id, request_id). 실행 접수와 같은 트랜잭션에서 추가한다. |
| steps. | run_id FK, step_id, ordinal, status, exit_code nullable, observed_json. PK(run_id, step_id), UQ(run_id, ordinal). |
| case_results. | run_id FK, test_id, attempt, requirement_id nullable, status, severity, expected_json nullable, observed_json nullable, location_json nullable. PK(run_id, test_id, attempt). |
| evidence. | id PK, run_id FK, relative_path, sha256, byte_length, mime, sensitivity, state. UQ(run_id, relative_path). 상태는 staged/ready/missing/quarantined. |
| gaps. | id PK, project_id FK, requirement_id nullable, opened_run_id FK, resolved_run_id FK nullable, kind, state, detail_json. 닫힌 공백도 이력을 보존한다. |
| resources. | id PK, run_id FK, kind, owner_token_hash, state, descriptor_json, cleanup_json nullable. 외부 자원의 정확한 ID·PID/시작시각·생성 의도를 기록한다. |
| events. | run_id FK, sequence, type, recorded_at, payload_json. PK(run_id, sequence). 이벤트 재수신은 멱등 처리한다. |
| audit_events. | id PK, action, actor_kind, entity_id, before_hash nullable, after_hash nullable, approval_id FK nullable, recorded_at, detail_json. 기록은 추가만 한다. |

project의 활성 카탈로그와 plan의 workspace/catalog가 같은 project인지 트랜잭션 안에서 검증한다. requirement/check 연결은 kind 열을 상수로 제한한 복합 FK를 사용한다. 실행별 testId·기준은 plan JSON의 고정 목록을 참조하므로 이후 활성 카탈로그가 바뀌어도 결과가 달라지지 않는다. `origin`은 live/imported이고 imported 실행의 현재 verdict는 unknown이다. DB 무결성 제약과 도메인 검증 둘 다 적용한다.

주요 인덱스는 runs(workspace_id, started_at DESC, id), runs(state), case_results(run_id, status), evidence(run_id, state), gaps(project_id, state), audit_events(entity_id, recorded_at)다. 요청·카탈로그·이벤트 중복은 고유 제약으로 막는다. 기본 조회 페이지는50개, 최대100개, 마지막 시간과 ID를 함께 넣은 cursor를 사용한다.

WAL·foreign_keys ON·busy_timeout 5000ms·synchronous FULL을 사용한다. 서비스의 쓰기 큐 하나로 짧은 트랜잭션을 수행하고 외부 명령·다운로드·파일 복사를 트랜잭션 안에서 기다리지 않는다. timeout은 storage-busy로 반환하며 새 실행번호를 중복 발급하지 않는다. DB 파일을 네트워크 드라이브나 동기화 폴더에 두지 않는다. 앱·CLI·worker가 각각 쓰기 연결을 만들지 않는다.

## 3. 파일과 DB 확정 순서.

1. 시작 접수에서 계획·승인 범위·작업 폴더 잠금을 확인하고 runs/requests를 한 트랜잭션으로 추가한다. 이 기록이 확정되기 전에 worker를 시작하지 않는다.
2. worker는 실행별 이벤트 파일에 순서 번호를 기록하고 수집한 증거를 같은 볼륨의 임시 파일로 작성한다. 파일 닫기·해시·경로 검사 후 최종 파일명으로 변경한다.
3. 서비스가 증거 실재·크기·해시를 확인한 다음 ready로 등록한다. 이벤트는 (runId, sequence)로 중복 삽입을 막는다. 전체 원본 로그를 DB에 중복 저장하지 않는다.
4. worker가 단계 완료와 정리 결과를 보고한 뒤 종료한다. 서비스는 실제 종료코드, 최종 소스·환경 지문, 필수 증거·정리 결과를 확인한다.
5. 최종 결과와 finalized_at을 DB 트랜잭션으로 확정한 후 최종 성공을 응답한다. 내보내는 JSON/HTML은 이 확정 결과에서 생성하며 별도 판정 원본이 아니다.

증거 파일 작성 후 DB 기록 전에 중단되면 해당 실행의 소유 manifest와 해시를 검증해 재등록할 수 있다. DB에 ready인데 파일이 없거나 달라지면 증거 손상으로 표시하고 정상 증거로 제공하지 않는다. 이미 확정된 과거 판정은 지우지 않고 현재 `integrity=degraded`와 원인을 붙여 재사용 가능한 통과로 취급하지 않는다. 실행 중 원본이 바뀌거나 복구에서 종료를 확인하지 못하면 통과로 확정하지 않는다.

DB 손상은 자동 재생성하지 않는다. 쓰기를 중지하고 진단·복구 안내를 제공한다. 백업은 better-sqlite3의 backup API와 증거 manifest를 사용한다. 살아 있는 DB 본체만 단순 복사해 WAL 내용을 누락하지 않는다. 백업 묶음은 기준 시각의 DB와 참조 증거·체크섬을 포함하고 백업 중 참조 자료를 정리하지 않는다. 복구는 별도 위치에서 무결성·참조 파일을 검사한 뒤 사용자 확인 후 교체한다. [SQLite 백업](https://www.sqlite.org/backup.html).

마이그레이션은 서비스 유휴·단독 접근·백업 성공·구체적인 영향 확인 후 순서대로 적용한다. 적용 checksum이 다르면 중단한다. 첫 버전은 자동 삭제와 다운 마이그레이션을 제공하지 않는다. 정리는 runId·파일·연관 행·예상 용량을 미리 보여주고 확인한 범위만 처리한다. 부분 실패는 삭제된/남은 항목을 각각 기록한다.

## 4. 공개 CLI와 MCP.

| 목적 | CLI | MCP |
|---|---|---|
| 로컬 실행 환경 진단. | `checkmate doctor --json`. | 없음. 서비스에 연결하지 않는다. |
| 연결된 자료와 기능 조회. | `checkmate capabilities --json`. | `get_capabilities`. |
| 프로젝트 조회. | `checkmate projects`. | `list_projects`. |
| 검사 목록. | `checkmate checks --project ID`. | `list_checks`. |
| 사전 계획. | `checkmate inspect --project ID --profile quick`. | `inspect_project`. |
| 실행 접수. | `checkmate run --plan ID --request-id ID`. | `start_run`. |
| 상태. | `checkmate status RUN`. | `get_run_status`. |
| 결과. | `checkmate result RUN --section summary`. | `get_run_result`. |
| 증거. | `checkmate evidence RUN EVIDENCE`. | `get_evidence`. |
| 취소. | `checkmate cancel RUN`. | `cancel_run`. |
| 이력. | `checkmate history --project ID`. | `list_runs`. |
| 공백. | `checkmate gaps --project ID`. | `list_gaps`. |
| 원본 재동기화. | `checkmate catalog sync --project ID`. | `sync_catalog`. |
| AI 서버 시작. | `checkmate mcp`. | stdio 진입점. |
| 결과 파일 검사. | `checkmate report validate FILE --json`. | 없음. 로컬 개발/진단용 읽기 전용 명령. |

`capabilities`와 `get_capabilities`의 `data.connection.dataRoot`는 요청을 처리한 서비스의 실제 자료 폴더 절대 경로다. 클라이언트가 지정했다고 추정한 경로가 아니다. 이 값과 `projects` 또는 `list_projects`의 프로젝트 ID·realPath를 함께 대조한 뒤 계획을 만든다. 자료 경로를 제공하지 않는 내장 서비스는 `connection: null`을 반환하며, 구버전의 필드 누락도 경로 미확인으로 취급한다. 연결 비밀·환경 변수·인증 값은 응답에 포함하지 않는다. 자료 폴더를 바꾸려면 CLI의 `--data-dir` 또는 해당 MCP 연결 인자를 확인하며, 프로젝트를 중복 등록하거나 자료를 복사해 해결하지 않는다.

프로젝트 등록과 실행 권한 부여는 사람용 GUI 또는 로컬 CLI 설정 흐름에서 한다. MCP의 sync_catalog는 이미 등록한 루트만 읽으며 변경안과 필요한 확인을 반환한다. UI 승인 없이 활성 기준을 변경하지 않는다. 모델이 호출하는 도구에는 승인 생성·임의 SQL·명령 문자열·임의 증거 경로 입력을 제공하지 않는다.

요청은 `{ apiVersion: 1, requestId, ...입력 }`, 응답은 `{ apiVersion: 1, ok, data?, error?, nextCursor? }`다. 알 수 없는 입력 키·지원하지 않는 major 버전은 거절한다. 응답의 추가 선택 필드는 minor 호환으로 취급한다. MCP 프로토콜의 오류와 도메인 오류를 구분하고 SDK의 표준 반환 형식을 유지한다. stdout은 MCP 메시지 또는 요청한 JSON 하나만 사용하며 로그는 stderr로 보낸다.

`inspect_project` 입력은 projectId/profile, 결과는 준비 상태·planId·지문·필수 검사·쓰기 계획·필요 승인이다. `start_run`은 projectId, planId, requestId를 받으며 계획이 없거나 낡았으면 실행하지 않는다. 같은 요청은 같은 실행을 돌려준다. 시작 요청의 성공은 접수 성공이며 검사 통과가 아니다. 취소도 접수와 종료 확인을 구분한다.

`get_run_result`의 section은 summary/cases/gaps/repair-bundle이다. `get_evidence`는 runId/evidenceId/cursor/limit를 받고 경로를 받지 않는다. UTF-8 JSON8KiB 제한은 항목 수를 줄여 지키고 JSON 문자열 중간을 잘라내지 않는다. 안전한 본문 조회는 최대32KiB, 기본8KiB다. 이미지·trace는 기본 응답에 첨부하지 않는다. 불투명 cursor를 다른 실행·필터에 재사용하면 거절한다.

| CLI 종료코드 | 뜻 |
|---|---|
| 0. | 조회·접수 성공. `run --wait`에서는 최종 passed만0. |
| 1. | 실제 검사의 failed. |
| 2. | 입력·계약·사용법 오류. |
| 3. | 준비 부족·확인 필요·필수 미실행 등 incomplete. |
| 4. | 사용자 취소. |
| 5. | 출처·생존·종료·정리·증거 확인 불가 또는 저장 오류. |
| 6. | 지원하지 않는 API/스키마 버전. |
| 7. | 요청 ID 충돌·계획 노후화·동시 작업 충돌. |

도메인 오류는 code, 한국어 message, retryable, nextAction을 갖는다. 주요 code는 invalid-input/unsupported-version/project-not-found/needs-approval/plan-stale/request-conflict/workspace-busy/environment-mismatch/storage-busy/storage-error/evidence-missing/ownership-unknown이다. 오류를 빈 성공 결과로 바꾸지 않는다.

## 5. 실행 결과와 어댑터 이벤트.

공통 결과는 schemaVersion, runId, projectId, profile, origin, state, verdict, planHash, sourceBefore/sourceAfter, workerExitCode, environmentVerified, evidenceVerified, cleanupVerified, finalized, plannedChecks, requiredChecks, cases, reasons를 필수로 갖는다. plannedChecks는 선택 계획의 전체 검사 ID이며 필수 검사와 개별 결과가 이 목록에 속하는지 확인한다. 과거 자료의 확인할 수 없는 값은 null 또는 unknown으로 보존하며 합성한 기대값을 넣지 않는다. 필수 검사가 없는 프로필은 빈 성공으로 처리하지 않는다. 자기 진단은 업무 검사 실행과 별도 응답이다.

개별 결과는 testId, status, requirementId nullable, expected/observed nullable, evidenceIds, severity, location nullable를 갖는다. status는 passed/failed/not-run/skipped/timed-out/interrupted/unknown이다. 필수 검사마다 실제 결과가 있어야 하며 중복 testId나 계획 밖 결과는 계약 오류다. 반복 시도는 별도 attempt와 최초 결과를 보존하는 확장으로 도입하며 첫 버전은 자동 재시도하지 않는다.

데스크톱 진행 조회는 별도 `progress` 요청에 `runId`를 전달한다. 응답은 실행 상태·확정 여부·진행 정보의 가용 여부, `phase`, 현재 명령 ID와 제목, 완료 명령 수·전체 명령 수·갱신 시각이다. 등록된 계획에 맞는 작업자의 실제 시작·종료 관측만 사용하며 명령 인자·환경·로그는 포함하지 않는다. 진행 응답에 판정을 넣지 않고 기존 8KiB 요약과 분리한다. 서비스 재시작·관측 오류·취소 후에는 진행 정보를 미확인으로 닫지만, 취소된 현재 명령의 유효한 종료·정리 결과는 계속 수집한다. 완료 명령 수는 통과한 검사 수가 아니다.

어댑터 이벤트는 UTF-8 NDJSON으로 protocolVersion/runId/sequence/type/time/payload를 가진다. 한 줄은64KiB 이내, sequence는 실행별 단조 증가한다. 유형은 step-started/case-result/evidence-created/resource-intent/resource-created/resource-cleaned/step-finished/worker-finished다. 원본 로그는 별도 파일로 스트리밍한다. 잘못된 줄·과대 메시지·runId 불일치·순서 충돌은 adapter-protocol-error로 남기고 전체 통과를 막는다.

자원 생성은 intent를 내구성 있게 기록한 후 수행하고 생성된 정확한 ID를 연결한다. 컨테이너에는 runId·소유 토큰을 전달하며 공통 label이나 시작 전후 차집합만으로 소유권을 추정하지 않는다. worker-finished 이벤트만으로 프로세스 정상 종료를 인정하지 않고 서비스의 종료 관측과 대조한다.

초기 실행기 기반의 직접 자식 프로세스 시험은 임시 DB 없이 실행 가능한 Node fixture를 사용한다. 전체 프로세스 트리·Docker·Windows 앱 종료 생존까지 확인하기 전에는 운영용 취소/복구가 구현됐다고 보고하지 않는다. 기반 단계의 보고서 검증 명령은 로컬 파일의 형식·내부 일관성을 검사할 뿐 파일 내용이 실제 테스트 증거라는 인증을 제공하지 않는다.

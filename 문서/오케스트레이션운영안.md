공식 기본 출발점은 Sol medium, Luna high, Astra low다. 위 추천은 체크메이트가 통과 판정과 프로세스·DB 안전성을 다루므로 핵심 작업의 강도를 올린 프로젝트 판단이다. 강도를 높이면 시간과 토큰 사용이 늘고 모든 작업의 품질이 비례해 개선되는 것은 아니다. [공식 모델 선택](https://learn.chatgpt.com/docs/models), [역할별 추론 강도](https://learn.chatgpt.com/docs/agent-configuration/subagents#choosing-models-and-reasoning).

Max는 어려운 한 문제의 원인 규명·설계 비교에 한정하고 전체 워커의 상시 기본값으로 두지 않는다. Ultra의 자동 위임과 Orca의 명시적 작업 지휘가 겹치지 않도록 이 운영에서는 xhigh/high/medium을 명시하고 총괄이 새 작업자를 관리한다. 워커는 추가 워커가 필요하면 총괄에게 요청한다.

Standard 공개 요율상 GPT-6 Sol은 GPT-5.6 Sol 대비 입력·캐시·출력 단가가 절반이다. 이는 같은 토큰 수의 요율 비교이며 구독의 실제 허용 작업량이나 총 소모가 정확히 절반이라는 뜻은 아니다. 현재 사용자의 계정별 잔여량은 확인하지 않았다. [속도와 사용량](https://learn.chatgpt.com/docs/agent-configuration/speed#fast-mode), [공개 크레딧 요율](https://learn.chatgpt.com/docs/pricing#token-rates).

## 작업을 나누는 방식.

총괄은 사용자 요구·설계·완료 기준·공유 계약·통합 Git 작업을 소유한다. 워커는 스스로 전체 설계를 바꾸지 않고 주어진 파일과 결과를 책임진다. 공통 결과 타입, 의존성 목록과 잠금 파일, 전체 실행 진입점은 총괄이 관리한다. 워커가 변경이 필요하면 정확한 이유와 최소 변경안을 총괄에 전달한다.

한 작업 명세에는 대상 파일, 변경할 동작, 읽을 기준 문서, 수정 금지 범위, 수용 시험, 제출할 증거를 반드시 넣는다. 채팅 전체를 매번 복제하는 대신 관련 문서 절과 실제 소스만 준다. 각 워커는 변경 파일·핵심 판단·시험 명령·종료코드·미해결 사항을 짧게 보고하고 큰 로그는 경로로 남긴다.

첫 저장·서비스 구현은 아래 순서로 진행한다.

| 순서 | 담당과 소유 범위 | 병렬 조건과 수용 기준 |
|---|---|---|
| 1. 계약 고정. | 총괄이 저장 인터페이스·실행 접수·이벤트·오류 계약과 시험 경계를 고정한다. | 워커 둘이 공통 타입을 서로 다르게 정의하지 않게 한다. |
| 2A. 저장. | 구현 A가 `packages/engine/src/저장/`과 전용 시험을 소유한다. | 카탈로그·실행·요청 중복·증거 확정·트랜잭션·복구를 구현한다. DB 시험은 구체적 승인 뒤 실행한다. |
| 2B. 서비스. | 구현 B가 `packages/engine/src/서비스/`와 전용 시험을 소유한다. | 고정한 저장 인터페이스의 메모리 대역으로 접수·큐·수명·취소·재접속을 먼저 검증한다. |
| 3. 통합과 검토. | 총괄이 실제 저장과 서비스를 연결하고 독립 검토자가 고정된 변경을 검토한다. | 중복 요청은 같은 runId, 강제 중단·정리 미확인은 통과 금지, 다른 세션 자원 보존. |
| 4. 세 입구. | 공통 서비스 안정화 후 CLI/MCP와 Electron 화면을 파일 영역별로 나눈다. | 같은 실행을 같은 상태·판정·증거로 조회한다. 화면은 임시 기대 데이터와 실제 검증 결과를 명확히 구분한다. |

목표는 한 번에 많은 파일을 만드는 것이 아니라 검사1개를 계획→실행→저장→조회→취소/복구까지 연결하는 작은 완성 단위다. 그 단위를 확인한 후 대상 검사·다섯 기능으로 넓힌다. 모든 단계에 워커를 붙이지 않으며 공유 계약 확정과 통합처럼 순서가 필요한 일은 직렬로 처리한다.

## 파일·Git·실행 충돌 방지.

현재처럼 같은 작업 폴더를 쓰는 경우 파일 소유권을 겹치지 않게 하고 Git 추가·커밋·브랜치 변경·의존성 설치·전체 빌드는 총괄이 순서대로 수행한다. 워커가 쓴 파일도 다른 워커의 현재 변경일 수 있으므로 실패를 보고 임의로 되돌리지 않는다. 전역의 의미 단위 커밋 규칙은 통합 담당인 총괄이 각 작업 결과를 확인한 직후 충족한다.

소스와 빌드 산출물이 겹쳐 동시에 안정적으로 시험할 수 없거나 고정 커밋의 검토가 필요한 경우 Orca의 별도 작업 폴더를 사용한다. 읽기 전용 검토도 이동 중인 파일을 읽지 않게 검토 기준 커밋을 고정한다. 검토자가 같은 파일을 직접 고치지 않고 발견 사항을 구현 담당에게 보낸다. 별도 브랜치는 전역 work 이름 규칙과 승인된 기준을 따르며 불필요한 작업 폴더는 미리 만들지 않는다.

검증은 워커의 해당 영역 시험 → 통합 후 전체 시험 → 독립 검토 순서다. 코드가 바뀌지 않았는데 모든 워커가 같은 전체 시험을 반복하지 않는다. 독립 검토는 중요한 실패 경로를 직접 확인하되 단순히 같은 체크리스트를 다시 읽는 역할로 끝내지 않는다.

## Orca 실행 계약.

이번에는 실행하지 않은 권장 절차다. 아래 모델은 사용자 선택으로 추천안을 채택한 뒤 새 워커에 명시한다. 그 전에는 전역 기본값 `gpt-5.6-sol / high`가 유효하다.

1. 런타임 준비를 확인하고 현재 총괄 터미널에 Run 하나를 연결한다.
2. 기준·소유 파일·수용 시험이 정해진 Task를 만든다. 실제 순서가 필요한 작업에만 의존성을 둔다.
3. 준비된 독립 작업을 모두 시작한 뒤 기다린다. 시작 명령의 요청값과 실제 적용값, 준비 완료를 확인한다.
4. 질문·진행·완료는 Orca의 같은 Run/Dispatch로 추적한다. 총괄이 권한을 소유하며 워커의 임의 추가 워커 생성을 금지한다.
5. 완료 메시지를 실제 파일·시험 결과와 대조한다. 승인된 완료 정산 뒤 즉시 재사용하거나 해제하며 살아 있는 워커를 방치하지 않는다.

새 워커의 명령 형식은 설치된 Orca 도움말에서 확인했다.

```powershell
orca orchestration worker-start --task '<task-id>' --worktree current --agent codex --model gpt-6-sol --effort high --json
```

기존 터미널 재사용은 `--model/--effort` 변경과 함께 할 수 없다. 모델을 바꿔야 하면 새 워커를 만든다. 재사용했는데 새 모델이 적용됐다고 보고하지 않는다. 통신 끊김이나 빈 상태 조회를 종료로 간주하지 않고 원래 실행의 상태를 확인한다. 확실하지 않은 작업을 복제하거나 다른 세션의 프로세스·잠금을 종료하지 않는다.

이 제품 개발의 오케스트레이션은 현재 구독 로그인한 Codex를 사용하며 제품에 모델 API 호출을 추가하는 작업이 아니다. 여러 워커의 모델 사용은 같은 구독의 사용 한도를 소모할 수 있으므로 무제한 실행으로 취급하지 않는다.

## 단계 진입과 운영 조정.

다음 DB 단계는 `C:/dev/E2E/.runtime/` 아래의 시험 전용 관리 DB와 해당 테스트가 만드는 테이블·작업·삭제 조건·예상 범위를 먼저 제시해 확인받는다. 승인 전에는 마이그레이션이나 DB를 생성하는 시험을 실행하지 않는다. 운영/아틀리에 DB와 기존 사용자 관리 DB는 이 범위에 들어가지 않는다. 테스트 코드를 작성할 수 있다는 사실을 실행 승인으로 바꾸지 않는다.

첫 두 완성 단위에서 소요 시간, 재작업 횟수, 통합 충돌, 독립 검토의 중대 누락, 확인 가능한 모델 사용량을 기록한다. 쉬운 작업이 high에서 지연되면 medium으로 낮추고, 같은 복잡한 결함을 반복 놓치면 작업 문맥과 수용 기준을 보완한 뒤 해당 워커만 강도를 올린다. 실제 측정 없이 특정 조합이 몇 배 빠르거나 비용을 몇 퍼센트 절감한다고 약속하지 않는다.

이 문서 작성 시 사용한 근거는 현재 공식 OpenAI 문서, Codex의 실제 설정과 모델 목록, 설치된 Orca가 제공한 orchestration·coordinator-loop·placement-and-remote 가이드다. 새 워커를 띄우는 기능 시험과 계정 사용 한도 확인은 아직 하지 않았다.

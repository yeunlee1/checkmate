# 제품 방향과 차별화 후보.

2026-09-25 사용자 지시를 반영한다. 사용자는 직전 제안한 기본 스택 방향을 수용했고, 대기업이 개발한 제품으로 느껴질 수준의 완성도를 요구하며 우리 E2E의 특별한 기능을 물었다.

## 1. 확정한 기본 방향.

- 공통 엔진은 Node.js와 TypeScript로 개발한다.
- CLI와 로컬 stdio MCP가 같은 엔진과 결과 계약을 사용한다.
- 사람은 로컬 웹 화면과 한국어 보고서를 사용한다.
- 최초 결과 저장은 JSON·NDJSON·캡처·로그 파일이다. E2E 관리용 DB는 먼저 도입하지 않는다.
- 기존 Playwright·Vitest·Node 검사를 연결한다. 아틀리에의 DB 검증에는 격리 Docker PostgreSQL을 사용한다.
- 프론트 프레임워크, CLI/HTTP/MCP 라이브러리, 정확한 버전과 배포 포장은 아직 선정하지 않았다. 기본 스택 수용을 미제안 세부 기술의 승인으로 확대하지 않는다.

이 문서는 [개발 설계](개발설계.md)의 추천 기술에 대한 후속 결정을 기록한다. 이전 검토본 두 문서는 그때의 사실 확인 증거로 보존하며, 이번 사용자 결정이 우선한다.

## 2. 제품 품질 목표.

대기업 수준이라는 표현을 달성했다고 선언하는 대신 아래 기준을 실제 릴리스 검사로 확인한다. 임의의 품질 점수나 토큰 절감률을 약속하지 않는다.

| 기준 | 제품에서 확인할 내용 | 완료 증거 |
|---|---|---|
| 판정 신뢰성 | 실패·미실행·불확실·기준 변경·환경 불일치를 정확히 구분한다. | 의도적인 실패와 중단에서 거짓 통과가 나오지 않는 자체 회귀 시험. |
| 사람이 이해하는 화면 | 프로젝트→실행→문제→증거의 이동이 일관적이다. 빈 상태·오류·로딩·키보드·가독성도 설계한다. | 대표 사용자가 주요 실패3건의 이유와 다음 행동을 설명할 수 있는 사용성 확인. |
| 실행 복구 | 중복 호출·연결 끊김·프로세스 비정상 종료 뒤 상태와 소유 자원을 추적한다. | Windows에서 취소·timeout·재접속과 다른 세션 자원 보존 시험. |
| 자료 보호 | 실자료 접속·비밀 값 노출·임의 명령/파일 접근을 막는다. | 격리 환경·가짜 비밀 값·권한/경로/HTML 공격 회귀 시험. |
| 설치와 업데이트 | 지원 환경·필수 도구·첫 실행·설정 오류가 분명하다. 기존 기록을 보존한다. | 깨끗한 지원 환경에서 설치/진단/첫 실행, 이전 결과 형식 호환 시험. |
| 응답과 비용 | 기본 결과는 짧게 제공하고 큰 이력은 나누어 읽는다. | 명시한 기준 PC·이력 규모에서 응답시간·메모리·출력 바이트를 측정. 수치 목표는 첫 측정 뒤 확정. |

첫 제공 범위를 작게 유지하더라도 그 범위의 오류 처리·마감·안내까지 완성한다. 제공 단계 M0/M1/M2는 그대로 유지하며 초기 시연을 전체 업무 E2E 완성으로 표시하지 않는다.

## 3. 기존 도구와의 관계.

Playwright는 이미 테스트 계획·생성·수정 에이전트와 trace 탐색을 제공한다. 의도적 코드 변이로 테스트의 검출력을 확인하는 mutation testing도 기존 기법이다. 이를 처음 발명한 기능으로 설명하지 않는다.

우리 제품의 차별화 제안은 한국어 업무 요구사항, 실제 실행 근거, 사람이 내릴 판단, AI가 수정에 필요한 자료를 같은 실행 기록으로 연결하는 사용 흐름이다. 아래 후보는 시장 전체의 독점 기능을 주장하는 목록이 아니며 사용자 선택 전에는 추가 구현 범위로 확정하지 않는다.

## 4. 후보 기능.

### 후보-01. 기능별 완료 근거.

요구사항별로 구현 상태, 연결된 검사, 최신 실행 환경, 실제 결과, 빠진 증거를 한 카드에서 보여준다. 예를 들어 견적 저장은 화면 동작·API 결과·재조회·금액·중복 요청 검사를 나누어 표시한다. 화면 검사만 통과했다면 DB 저장과 중복 방지는 미검증으로 남긴다.

입력은 명시적으로 등록한 요구사항 ID와 검사 매핑이다. 문서 전체를 완벽하게 이해해 누락을 자동 발견했다고 주장하지 않는다. AI가 매핑을 제안할 수 있지만 사람이 확인한 기준과 추정 후보를 구분한다.

증거 카드에는 소스·검사·기준 버전과 실행번호를 고정한다. 필요하면 화면 행동→요청→응답→저장 확인을 연결하되 같은 run/request의 계측 근거가 있을 때만 연결하고 없으면 '연결 증거 없음'으로 표시한다. 해시는 변경 대조 수단이며 같은 OS 권한을 가진 주체의 조작을 막는 서명 증명서는 아니다.

기존 공통-01·결과-02·신뢰-01의 정보를 사람이 기능 단위로 이해하게 만드는 확장이다. 첫 대표 기능으로 추천한다.

### 후보-02. AI 수정용 전달 묶음.

실패 한 건에 대해 요구사항, 재현 조건, 기대/실제 차이, 해당 소스 위치, 안전한 로그 발췌, 증거 ID, 재검사 계획을 짧게 제공한다. 예를 들어 '같은 요청을 두 번 보냈을 때 견적이 두 개 생김'의 실행과 자료를 즉시 찾게 한다.

기본 수집과 묶음 생성에는 LLM이 필요 없다. 원인이 입증된 부분과 추정은 구분한다. 관련 파일 위치도 stack·test location·명시적 매핑에 근거하며 수정해야 할 파일을 확정했다고 표시하지 않는다. 필요할 때만 추가 증거를 요청한다.

MCP는 짧은 결과를 반환하고, 사람은 같은 내용의 한국어 카드와 'AI에 전달할 내용 복사'를 사용한다. 재검사 요청은 기존 계획·승인 경계를 유지한다. 보고서에서 받은 문장을 셸로 실행하지 않으며 도구가 업무 코드를 자동 수정하지 않는다.

기존 결과-04·보안-02를 구체화한 확장으로 후보-01과 함께 첫 대표 기능으로 추천한다. 실제 토큰 절감은 동일 과제의 모델 사용량으로 측정한다.

### 후보-03. 역할별 정보 노출 검사.

가상 owner와 staff/developer 계정에 같은 가상 데이터를 준비하고, 허용된 정보와 금지된 정보가 UI·DOM·API 응답·내보내기 등에 어떻게 나타나는지 검사한다. 화면에 원가가 안 보이더라도 응답에 금지 필드가 있으면 해당 경로를 실패로 표시한다.

프로젝트가 역할별 공개 필드·API·출력 경로와 가짜 민감값을 명시해야 한다. 계정별 모든 차이를 누출이라고 판정하지 않는다. 검사한 경로 밖의 유출까지 없다고 보장하지 않는다. 실제 고객/원가 자료는 쓰지 않는다.

아틀리에의 일반 직원 관리 권한부터 적용할 수 있다. owner 전용 원가/매출은 미래 업무 기능이므로 해당 구현 후 연결할 후보이며 현재 앱에 존재한다고 표시하지 않는다. 기존 보안-01보다 노출 경로를 넓히는 추가 기능이다.

### 후보-04. 테스트 자체의 검출력 확인.

격리된 코드/가상환경에 작은 결함을 넣고 어떤 검사가 실패하는지 확인한다. 견적 합계 계산 변경, 권한 거절 누락, 저장 오류 후 성공 표시 같은 제한된 결함을 후보로 삼는다.

원본 업무 코드를 변경하지 않으며 실제 DB에 실행하지 않는다. 모든 변이를 매번 전체 브라우저로 실행하지 않고 핵심 순수 계산·권한 규칙부터 시작한다. 동작이 같은 변이, 환경 오류, timeout과 실제 결함 검출은 구분한다.

기존 완료 기준의 의도적 결함 시험을 사용자 기능으로 확장하는 제안이다. 테스트 품질의 일부 근거이며 전 결함 탐지 보장은 아니다. 계산 비용이 커질 수 있어 후속 후보로 둔다.

### 후보-05. 디자인 위반 위치와 이유 표시.

캡처 위에 규칙을 어긴 요소를 표시하고 기준·관측·화면 폭·관련 요소를 설명한다. 예를 들어 승인된 버튼 높이와 관측 높이의 차이, 화면 밖으로 벗어난 저장 버튼, 실패한 대비 검사 결과를 보여준다.

색·타이포·배치·키보드·접근성 규칙과 픽셀 변화, 주관적 미감 판단을 분리한다. 승인된 수치만 합격/불합격 기준으로 쓴다. 새 화면에 기준이 없으면 '기준 필요'이며 임의의 점수로 디자인 완성도를 확정하지 않는다.

기준 이미지·기대값·허용 오차가 코드 수정과 함께 바뀌면 전후 차이를 사람의 확인 목록에 올린다. 기준 변경 자체를 잘못된 수정으로 단정하지 않는다. 실패를 숨기기 위한 자동 기준 교체는 허용하지 않는다.

기존 화면-02·결과-03의 표현을 구체화하는 확장이다. 확정된 시각 기준을 가진 화면부터 적용한다.

## 5. 우선 제안과 다음 결정.

첫 대표 기능은 후보-01과 후보-02의 연결을 추천한다. 사람은 '무엇이 끝났고 무엇을 더 봐야 하는지'를 알 수 있고, AI는 실패한 부분의 증거를 받아 수정할 수 있다. 기존 실행·보고 계약을 활용하므로 별도 AI 플랫폼이나 대규모 서비스부터 만들 필요가 없다.

후보-03은 업무 보안 규칙과 연결하고, 후보-05는 화면별 기준이 생기는 순서에 맞춘다. 후보-04의 일반화는 기본 실행기가 안정된 뒤 검토한다. 현재는 추천 순서이며 다섯 후보를 모두 첫 릴리스에 포함하기로 확정한 것은 아니다.

## 6. 공식 자료.

- [Playwright Test Agents](https://playwright.dev/docs/test-agents). 계획·생성·수정 에이전트가 이미 제공된다.
- [Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer). 브라우저 행동·DOM·네트워크 등의 실패 증거를 탐색할 수 있다.
- [Stryker의 mutation testing 설명](https://stryker-mutator.io/docs/). 코드에 변이를 넣고 테스트가 이를 탐지하는지 확인하는 기법이다.

이번 변경은 기본 방향 기록과 후보 제안이다. 제품 소스·테스트·DB는 실행하거나 변경하지 않았다.

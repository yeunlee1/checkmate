# 회사 PC와 다른 사용자의 체크메이트 설치 및 사용.

CheckMate는 Windows x64용 로컬 검사 앱이다. 공개 설치 파일을 받아 각 사용자의 PC에 설치할 수 있으며 앱 실행을 위해 제작자의 계정, GitHub 로그인, Git 또는 별도의 Node.js 설치가 필요하지 않다. AI 기능은 사용자가 이용하는 AI 클라이언트에 연결하며 CheckMate 자체는 모델 API 키를 요구하지 않는다.

## 설치.

1. [공식 릴리스](https://github.com/yeunlee1/checkmate/releases/latest)에서 `CheckMate-Setup.exe`를 내려받는다. GitHub가 함께 표시하는 Source code 압축 파일은 개발 소스이며 설치 파일이 아니다.
2. 같은 릴리스의 `SHA256SUMS.txt`에서 설치 파일 이름과 SHA256을 확인한다. PowerShell의 `Get-FileHash -Algorithm SHA256 -LiteralPath ./CheckMate-Setup.exe` 결과와 비교할 수 있다.
3. 설치 파일을 실행하고 시작 메뉴에서 CheckMate를 연다. 앱은 현재 Windows 사용자 아래에 설치되며 다른 사용자는 자기 계정에서 설치하고 자기 자료를 준비한다.
4. 첫 화면에서 자료 위치를 확인하고 로컬 저장소를 준비한다. 기본 앱 위치는 `%LOCALAPPDATA%/CheckMate`, 검사 자료는 별도 `%LOCALAPPDATA%/CheckMateData`다.

현재 공개 설치본은 코드 서명되지 않았다. 회사 정책에서 무서명 실행 파일을 막으면 IT 담당자의 승인된 설치 절차를 따른다. 앱은 조직의 실행 정책을 우회하지 않는다. macOS, Windows ARM과 Linux용 데스크톱 설치 파일은 이번 릴리스에 포함하지 않는다.

## 첫 프로젝트 검사.

1. 검사할 프로젝트를 이 PC의 실제 폴더에 준비한다. 다른 PC의 경로 문자열이나 실행 중인 자료 폴더를 그대로 복사해 연결하지 않는다.
2. 프로젝트에는 `checkmate/프로젝트.json`, `checkmate/요구사항.json`, `checkmate/검사항목.json`과 실제 검사 스크립트가 필요하다. 앱의 도움말과 [검사 작성 안내](검사작성안내.md)를 참고한다.
3. 앱에서 **프로젝트 → 프로젝트 추가**로 해당 폴더를 선택한다. 같은 저장소의 작업 폴더가 여러 개면 실제 실행할 작업 폴더를 선택한다.
4. 검사 묶음과 계획을 열어 실제 명령 및 파일 쓰기 범위를 확인하고 승인한다. 소스나 검사 기준이 바뀌면 새 계획을 확인한다.
5. 실행 결과에서 최종 판정과 증거 및 정리 상태를 확인한다. 진행 중인 통과 표시만으로 전체 완료를 판단하지 않는다.

앱과 엔진용 Node 및 기본 의존성은 설치본에 포함된다. 검사 대상 프로젝트의 런타임, 패키지, 브라우저와 외부 도구는 그 프로젝트의 요구사항에 따라 별도로 준비한다. Docker는 Docker 자원 프로필에만 필요하다. Windows 네이티브 PostgreSQL은 선택 기능이며 사용할 때 설치된 실행 파일의 실제 경로, 버전 및 지문을 등록하고 검증한다. 앱이 PostgreSQL을 자동 설치하지 않는다.

## AI 클라이언트 연결.

앱의 **설정 → MCP 실행 정보 → 명령과 인자 보기 → 설정 값 복사**에서 이 PC의 정보를 복사한다. 사용하는 AI 클라이언트의 MCP 설정에 복사한 `command`와 `args`를 추가한다. 집 PC나 제작자의 고정 경로를 넣지 않는다. AI 클라이언트 로그인은 각 사용자가 자신의 계정으로 수행한다.

연결 후 AI가 `get_capabilities`의 연결 버전과 자료 경로를 읽고, `list_projects`에서 실행할 프로젝트의 실제 경로를 확인하도록 한다. 프로젝트 등록과 계획 승인은 사람이 앱에서 한다. MCP 연결만으로 임의 폴더 실행 권한이 생기지 않는다.

여러 AI 세션은 각자의 연결과 실행 소유권을 사용한다. 같은 저장소의 여러 작업 폴더는 명시적으로 선택하고 공유 자원 잠금 경로를 임의로 나누지 않는다. 제어권을 넘길 때는 정확한 실행과 대상 소유자를 확인해 인계한다. 다른 PC 사이에서 실행 중인 엔진이나 잠금을 공유하는 구조는 아니다.

## 업데이트와 PC 이동.

Windows 설치 앱의 **설정 → 앱 업데이트**에서 새 버전을 확인한 뒤 내려받는다. 관리형 AI 연결은 유지하며 검사와 정리 완료 및 서비스의 자연 종료를 기다린다. 준비된 업데이트는 **재시작하여 업데이트**로 적용한다. 기존 연결의 최초 전환과 업데이트 뒤 연결 방식은 [업데이트와 AI 연결](업데이트와AI연결.md)을 확인한다.

기존 자료는 먼저 앱에서 백업하고 복구는 새 빈 폴더로 진행한다. 저장 버전1·2에서 버전3으로의 이행은 검증된 백업과 유휴 및 정리 상태를 확인한 뒤 사람의 명시적 절차로 진행한다. 프로젝트별로 지정한 출력 폴더의 등록 자료도 백업에 포함하며 복원 후에는 회사 PC에 맞는 폴더를 다시 선택한다. [프로젝트 자료 폴더](프로젝트자료폴더.md)에서 기존 자료 이전과 원본 보존 조건을 확인한다. 실행 중인 자료 폴더나 SQLite 파일을 Drive 실시간 동기화 대상으로 사용하지 않는다. 코드 이동은 프로젝트의 승인된 Git 원격과 인수인계 문서를 사용한다.

새 앱이 `migration-required`를 표시하면 새 설치본의 **MCP 실행 정보**에서 동봉 Node 명령, CLI 파일과 `--data-dir` 경로를 확인한다. 진행 중인 검사를 끝내고 해당 자료 폴더에 연결된 앱·AI 클라이언트를 정상 종료한 뒤, Node·CLI·`--data-dir` 경로는 유지하고 `mcp` 또는 `mcp-managed --installation-root …` 부분 전체를 `migrate-storage --confirm`으로 바꿔 사람이 실행한다. 이 명령은 기존 버전의 백업을 만들고 검증한 다음 이행하며 백업 경로와 지문을 반환한다. 사용 중인 서비스·남은 잠금·확인되지 않은 정리가 있으면 거절하므로 이를 강제로 해제하지 말고 원래 실행 상태부터 확인한다. 이행 성공 후 앱과 AI를 다시 열어 버전과 자료 경로를 대조한다.

## 확인한 범위.

릴리스의 실제 빌드·포장 앱·합성 업데이트 검증은 해당 GitHub Actions 기록과 [변경 내역](릴리스020변경내역.md)에 연결한다. 개발 PC와 별도의 GitHub Windows 실행 환경 검증을 회사의 보안 정책이나 모든 PC에서의 실기기 수용으로 확대하지 않는다. 회사 PC의 첫 설치와 실제 업무 프로젝트 검사는 그 PC에서 확인할 항목이다.

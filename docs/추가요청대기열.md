# CheckMate 추가 요청 대기열.

문서 개정은 r5이며 접수일은 2026-10-04다. 작성자는 `매니저 · W0 · 요청 정리`다. 원 요청 12개와 수용 기준을 유지하면서 최신 사용자 지시의 GitHub 게시·개발 PR 병합·main 릴리스 PR·태그·설치산출물 릴리스 게시·아틀리에 확인 요청 승인을 기록했다. v0.2.0은 준비·배포 대기이며 실제 운영 전환과는 구분한다. 이 문서는 접수 원장이고 반장의 실행 목록 `docs/수정요청목록.md`를 대신하지 않는다.

## 현재 지시와 권한.

- 이번 사용자 지시는 다중 AI 세션과 아틀리에 피드백의 **실제 수정 착수**다. 이슈 24의 과거 구현·배정 보류와 보고서의 당시 담당 수락 대기를 현재 개발 보류 근거로 사용하지 않는다.
- 총괄은 `term_7acee429-b646-4d63-a4cd-e54460da3c81`, 부모 Run은 `run_e878cdb4ed43`다. 이번 승인 접수 Task는 `task_8d1ab46f4b3e`, Dispatch는 `ctx_8725ee1a93b3`다. 이전 `task_b9acc38b5846 / ctx_8029686e69fa`와 최초 정리 Dispatch는 정산된 이력이며 이번 권한으로 재사용하지 않는다.
- CheckMate 개발 기준은 `5d3fe78d06e72d63680fc8e52538a28718eba24b`다. 아틀리에 비교 사본의 기준 `6aeb2c65d3258f60f76f8cb07dd9d5863f5dcdcf`와 섞지 않는다.
- 실제 자료·기존 서비스·설치본·보호 실행은 보존하면서 별도 개발 공간과 합성 시험으로 소스 개발을 진행한다. 사람 등록·승인이나 MCP 연결이 준비되지 않았으면 해당 통합 시험을 대기로 표시하고 독립 개발을 계속한다.
- 신뢰 등록·계획 승인·cleanup은 사람 전용이다. U3의 Git 게시·병합·릴리스 게시·확인 요청 승인은 명시적으로 기록하되 원 설치·MCP 서비스·보호 자료·실제 아틀리에 DB는 유지한다. 설치 교체·MCP 재연결·실사용 dataRoot 변경·보호 실행 정리·운영 DB 변경은 실제 운영 전환의 별도 범위다.
- 이번 매니저의 소유 파일은 이 문서 하나다. 변경 차이·문서 검사·인수인계 보고도 이 문서에 기록하며 이전 runtime 보관본·보고서는 수정하지 않는다. Git·코드·제품 검증·설치·MCP 호출을 하지 않으며 승인된 게시·병합·릴리스·아틀리에 확인 요청은 총괄의 실행 및 실제 근거 인수로 연결한다.

## 요청별 원 선행조건과 수용 기준 및 최신 상태.

원 요청의 의도·선행조건·수용 기준을 유지한다. 착수 당시의 설계·배정 조건과 이번 최종 상태를 구분하며 완료 범위는 U2의 지정 개발 수용에 한정한다.

### CM-001 · 오류 전달.

- 의도와 근거는 U1·S3·S4다. `project-conflict`와 `catalog-stale`이 `internal-error`로 축약된 순수 함수 재현을 최소 결함으로 분리한다. 여러 worktree 지원은 CM-003이며 오류 전달 수정으로 등록 제한을 자동 해제하지 않는다.
- 선행조건은 총괄의 공통 계약 소유권 확정과 별도 후보의 좁은 회귀 배정이다. S3의 소스 기준과 새 개발 후보가 다르므로 담당자가 현재 후보에서 적용 가능성을 확인한다.
- 수용 기준은 두 알려진 코드가 CLI·MCP 응답에 보존되고, 대조 코드 `workspace-busy`와 응답 스키마가 유지되는 것이다. 알 수 없는 코드와 민감한 원문 메시지·스택·비밀은 노출하지 않아야 한다. 제공하는 `nextAction`은 안전하고 사람 전용 경계를 바꾸지 않아야 한다.
- 최신 상태는 요청 r2·CM-001 소스 및 지정 개발 범위 수용이다. `29cfc499`의 좁은 4건·전체 근거와 최종 독립 수신을 연결한다. 원 오류 전달 실패는 이력으로 보존하고 설치·실사용 수용으로 확대하지 않는다.

### CM-002 · 실행 소유권과 인계.

- 의도와 근거는 U1·S1이다. 서비스가 확인할 수 있는 제어 권한으로 실행 소유자를 구분하고 타 세션의 취소·변경을 차단한다. 클라이언트가 자칭한 `sessionId`를 인증으로 사용하지 않는다.
- 선행조건은 총괄 소유 공통 계약의 호출 주체·제어 권한·사람 인계 설계와 CM-005의 영속 복구 경계다. 구체 API와 저장 형식은 구현 담당 검토 후 확정한다.

### CM-003 · 여러 worktree와 대상 경계.

- 의도와 근거는 U1·S1·S3이다. 같은 `repositoryIdentity`의 여러 worktree를 사람이 독립 등록하고 호출자가 명시 선택할 수 있어야 한다. 기존 원본 경로를 자동 교체하지 않는다.

- 최신 상태는 요청 r2·CM-004 지정 개발 범위 수용이다. 선언 writes/key 및 같은 host/user/commonlockRoot 경합과 최종 source·approval·owner·whole lease preflight에 연결한다. dataRoot 분리만으로 전역 경합 방지를 주장하지 않는다.

다음 4개는 **초기 r2의 매니저 제안 이력**이며 현재의 새 미배정 목록이 아니다. 원 제안과 사용자 지시의 구분을 유지한다. 최신 지정 개발 수용은 위 U2를 적용하며 이미 완료된 소스 분담을 다시 요청하지 않는다.

1. 총괄이 이 대기열을 반장 초기 분담 Task에 연결하고 CM-001의 좁은 오류 전달 수정부터 공통 계약 소유자가 처리하도록 배정한다. OP-003·OP-004의 역할 및 수신 연결을 함께 확인한다.
2. CM-002·CM-003·CM-005·CM-008의 공통 계약과 저장 경계를 먼저 직렬 확정한다. 반장이 실제 의존성과 파일 소유권을 확인한 뒤 독립 구현을 분담한다. 이 순서는 설치·사람 등록 대기와 무관하게 개발 공간에서 진행할 수 있다.
3. 확정된 경계에 CM-004·CM-007을 연결한다. CM-006의 별도 소유 wrapper·어댑터 개발은 파일·자원이 독립이면 병행할 수 있다. 합성 시험과 실패 반례를 보존하고 변경으로 무효가 된 범위만 다시 검증한다.
4. 단일 전담의 CM-006 MCP 수용과 OP-002 효과 비교는 사람 등록·실제 계획 승인·동일 후보 확인 후 진행한다. OP-001 설치/재연결은 별도 협의하고 최종 후보의 필요한 통합 검증을 한 번 배정한다.

현재는 **사용자가 명시 승인한 게시·병합·릴리스 PR·태그·설치산출물 릴리스 게시의 실행 대기 및 아틀리에 확인 요청의 전송·실제 수신 근거 인수 대기**다. 승인 자체를 다시 미확정으로 취급하지 않는다. OP-001의 원 설치/MCP 실제 운영 전환과 OP-002의 실제 아틀리에 정상·변이 비교·usage 계측·적용은 별도 미완료다. CM-006의 원 고정 표본도 OP-002와 연결해 남긴다. 원 unknown 304ms의 원문 유실·미재현·원인 미확정, 과거 Native unknown 2건과 보호 run 판정은 유지한다. 이번 매니저는 승인된 실행을 대행하거나 새 담당을 배정하지 않는다.

후속 갱신 시 같은 요청 ID·개정과 실제 담당·수신·후보·수용 근거를 이어간다. 원 요청 12개와 사용자 지시·제안·실패·보호 경계는 유지했다. 이번 문서 갱신과 총괄의 지정 개발 범위 수용은 설치·외부 게시·아틀리에 실사용 MCP·병합·출시 완료가 아니다.

## r5 변경 차이·문서 검사·인수인계 보고.

이번 변경은 U3의 명시 승인과 v0.2.0 준비를 추가하고 OP-001·OP-002·OP-004의 개정을 갱신한 것이다. 다른 9개 요청의 개정·원 조건·추천은 유지한다. 변경 전 r4 SHA256은 `AEA426C8ED8FC5F2A0A6195D908F964EA4ECEB54906165F66A055747BC92CFF2`이며 이전 보고·보관본·소스 파일은 수정하지 않았다.

진행은 승인 접수 → 12개 ID·조건과 보호 경계 유지 → 문서 차이·UTF-8·언어·ID·링크 검사 후 부모 Run 보고 순서다. 검사 결과는 아래에 갱신하고 최종 문서 지문은 worker_done에 전달한다. 별도 보고 파일이나 Git diff·Git 조회·제품 시험·설치·MCP 호출은 만들거나 실행하지 않는다. 접수 인계 완료와 실제 게시·병합·수신·적용 완료를 구분한 뒤 새 Task를 한 번 정산하고 사용자 요청 보존 세션을 유지한다.

# 체크메이트 동시 사용 개선 설계 제안.

## 확정 계약과 최종 인계.

총괄의 현재 지정 소스 검증 범위 기술 수용은 `msg_cc3ba6af3b39 / msg_b79a23e3100d`, 반장 경유 실제 수신은 `msg_a4258fe5b050`이다. 고정 제품 후보는 `cc4c01337a9c477f711f4311eb8959f981dfe272`다. 부반장은 구현을 대신하지 않고 코어, native PG·단일 wrapper, 회귀 보완, 독립 검토와 세 P2 보완 제출을 같은 관리 Task에서 연결했다. 상세 지문·실행 근거·자료 보존과 실제 수신은 [최종 제출 검토](../.runtime/동시사용개선/제출검토.md)에 있다. 아래 번호 1~10은 최초 조사와 순차 인수 당시의 기록이며 해당 시점의 대기·실패를 현재 상태로 승계하지 않는다.

- MCP 제어 주체는 서버가 발급한 owner와 서비스 수명에 결합한다. 자칭 sessionId를 인증으로 사용하지 않고 타 owner cancel과 재시작 후 이전 권한을 거절한다. 명시적 실행 인계는 사람 전용이며 legacy agent 제어를 안전하게 제한한다.
- 같은 repo의 다른 경로와 catalog를 동시에 등록하고 workspace를 명시적으로 선택한다. 모호한 생략과 다른 workspace의 plan/source를 거절하며 계획·승인·결과·history·cursor 경계를 유지한다.
- 같은 requestId는 저장된 본문과 owner를 다시 대조한다. 응답 유실과 재시작 unknown은 기존 결과 조회 및 fail closed로 처리하며 자동 재요청·TTL 추정 해제·사람 cleanup 대행을 하지 않는다.
- 공유 writes와 명시 자원 키는 기존 파일 잠금과 큐에 결합한다. 큐 출발 직전에는 기존 `checkedExecutionLease(runId)`를 재사용해 다른 run 참조·손상 JSON·행 부재를 차단한다. 소유 불명 파일 잠금과 자료를 보존한다.
- recordGaps 생성과 중복 검사는 현재 project/workspace/catalog를 유지한다. 해소는 같은 project/workspace의 과거 catalog까지 허용하되 원 openedPlan의 requirement 정의가 정확히 같아야 한다. testId가 있으면 check와 command도 정확히 같고 선택된 검사들이 통과해야 한다. null missing-test는 현재 required 검사가 한 개 이상이어야 한다. trusted/integrity/live/finalized/passed를 보존하고 다른 workspace·정의 변경·미선택·가져온 이력·unknown은 해소하지 않는다. 기존 openedRun과 final JSON은 불변이다.
- v1 SQL/checksum과 기존 strict RunResult/final JSON은 보존하고 workspace 연결, owner, admission과 resource metadata를 별도로 이행한다. 기존 자료·Docker omission·구클라이언트 조회를 무조건 제거하지 않는다.
- native PG는 기존 provider/executor/resourceStore/descriptor 경계를 사용한다. plan의 선택적 nativeResourceRoot를 불변 fingerprint와 사람 승인 범위에 결합하고 현재 provider root와 대조한 뒤 준비한다. binary·PID·시작 신원·cluster·port·marker·소유와 자손 종료 및 포트·자료 부재가 확인돼야 cleaned/verified로 판정한다.
- native cleanup은 family 관측 뒤 ownership과 PID 신원을 다시 결합하고 마지막 await 뒤 동기 실제 경로·marker SHA 검사를 수행한 뒤 정지한다. PID 경로 원문은 canonical native 표기와 Windows에서 backslash만 forward slash로 바꾼 정확 표기 두 개만 허용한다. resolve/trim·dot·dotdot·중복 separator·다른 경로로 별칭을 수용하지 않는다. version 관측 중 신원 변경 거절도 유지한다.
- 단일 검사 wrapper는 사용자가 선택한 정확 검사 ID를 등록 명령에 전달한다. 임의 셸 실행이나 선택 밖 검사로 확대하지 않는다. 별도 native 워커와 후속 보완 워커는 총괄이 순차 생성했고 부반장 하위 워커 생성은0이다.

현재 후보의 총괄 전체 시험은 빌드·타입 검사와 52파일 517통과/실패0/미실행3이고, 별도 새 합성 PG 두 클러스터 선택 시험은 1통과/실패0/필터 제외38이다. 수정 워커의 17반례/49영향과 후수정 독립 12시나리오도 별도 단계 근거로 구분하며 합산하거나 서로 대체하지 않는다. 설치 MCP·실제 Atelier·운영 효과 비교는 이 기술 수용에 포함하지 않는다. 원 unknown304ms 간헐 실패는 원인 미확정이고 원 실패·unknown2·lease6·cleanupfalse2를 보존한다. 실행은 현재 사용자 OS 권한의 로컬 과정이며 완전한 셸 권한 격리 보안으로 표현하지 않는다.

## 2. 작업 폴더 선택과 계획 경계.

- `projectId`는 저장소 정의 식별자, `workspaceId`는 정규화한 실제 경로의 등록 식별자로 둔다. 같은 프로젝트·repositoryIdentity의 서로 다른 실제 경로는 허용한다. 다른 프로젝트 ID로 같은 경로를 덮거나 repositoryIdentity 충돌을 숨기지는 않는다.
- `projects`는 기존 항목 형태를 유지한 작업 폴더별 행을 반환하는 최소안을 제안한다. 행에 기존 `id`, `workspaceId`, `realPath`, `activeCatalogHash`가 있으므로 새 배열 계층을 강제하지 않는다. GUI 행의 선택 키는 `(projectId, workspaceId)`다.
- `checks/inspect/sync/activate/history/gaps/import-history`에 선택 `workspaceId`를 추가한다. 생략은 작업 폴더가 하나인 경우만 기존 의미로 허용한다. 여러 개이면 G0의 `workspace-required`로 거절하고 첫 폴더·호출자 cwd·마지막 선택을 추정하지 않는다.
- `start`에도 선택 `workspaceId`를 받아 저장 계획의 project/workspace/path/catalog와 일치시킨다. 생략 시 계획의 명시된 작업 폴더를 사용하되 프로젝트만으로 폴더를 다시 고르지 않는다. 틀린 workspaceId·다른 projectId·불일치 plan JSON은 실행 전에 차단한다.
- 등록·카탈로그 활성화·실행 승인은 사람 전용으로 유지한다. sync는 선택 폴더의 후보를 저장·비교할 뿐 활성화하지 않는다. 다른 폴더의 활성화는 기존 계획과 승인에 영향을 주지 않는다.
- 계획 지문과 승인 scope에 workspaceId, 실제 경로와 경로 지문, catalogHash, sourceHash, 프로필, 선택 명령·writes·공유 자원·제공자 모드를 결합한다. 기존 계획의 JSON·지문·승인 자료는 재작성하지 않는다.
- `planContext/admitRun`은 프로젝트 활성 포인터 대신 선택 폴더의 활성 카탈로그를 검사한다. 동일 카탈로그 내용이면 프로젝트 내부 불변 카탈로그를 공유할 수 있다. 계획과 활성 연결은 작업 폴더별이다.
- 이력 목록·공백 목록·cursor는 작업 폴더와 필터를 포함한다. 공백 생성·해소는 openedRun의 workspace와 카탈로그 정의를 확인해 제한한다. 과거 이력 가져오기와 같은 원본 중복 검사도 선택 폴더별로 한다. 가져온 결과의 `unknown`은 유지한다.
- 결과 저장의 기존 strict `RunResult`와 `schemaVersion: 1`을 즉시 바꾸지 않는다. 저장 summary JSON에 새 키를 억지로 넣지 않고 status/result/history의 API 응답에 저장 run→plan→workspace의 대상 정보를 덧붙여 GUI와 MCP가 교차 결과를 거절하게 한다. 기존 HTML 내보내기·증거 접근의 runId 경계는 유지한다.
- GUI에서 작업 폴더를 바꾸면 계획·승인 체크·선택 실행·카탈로그 비교·페이지 cursor와 진행 응답을 무효화한다. 지연 응답은 선택 project/workspace/run과 일치할 때만 반영한다.

## 3. MCP 제어 권한과 사람 인계.

### 최소 권한 모델.

서비스가 암호학적 난수로 발급한 제어 credential과 공개 `ownerId`, 서비스 수명 `serviceEpoch`를 사용한다. 공개 ownerId와 사람이 붙인 label은 표시·인계 대상 선택용이며 인증 값이 아니다. dataRoot HMAC은 로컬 서비스 접근을 확인할 뿐 네 MCP 클라이언트를 구별하지 못한다.

1. 새 MCP 프로세스는 기존 v1 capabilities를 읽고 `agent-run-control` 지원을 확인한다. 지원 시 도구 목록에 노출하지 않는 IPC 내부 `open-agent-session` 요청으로 credential을 발급받는다. SDK tool 인자에 credential·sessionId를 받지 않는다.
2. credential은 MCP 프로세스 메모리에만 보관한다. 서비스는 현재 epoch의 검증 레지스트리를 소유하고 IPC 인증 단계가 검증한 `CallerContext`를 제품 서비스에 전달한다. 공개 요청 JSON의 자칭 ownerId·role·sessionId로 context를 만들지 않는다.
3. 요청마다 새 소켓을 여는 현재 방식에서도 같은 credential을 계속 사용한다. 같은 서버 수명의 연결 종료·재접속·유휴 조회는 제어권을 재발급하거나 취소하지 않는다. 살아 있는 MCP의 새 실행도 같은 ownerId에 연결한다.
4. 실행 최초 접수에 ownerId, 서비스 발급 credential의 owner proof hash, epoch를 내구성 있게 저장한다. 원문 proof는 저장하지 않는다. agent start의 기존 요청 재확인 및 agent cancel은 검증한 주체와 실행 소유권을 먼저 비교한다. B의 A 실행 취소는 executor·AbortController·DB 상태 변경 전에 거절한다.
5. 서비스 재시작은 메모리 credential을 무효화한다. 검증은 현재 serviceEpoch와 현재 발급 레지스트리를 모두 요구하므로 DB에 남은 owner hash만으로 이전 credential을 재인증하지 않는다. 이전 ownerId를 자칭하거나 이전 credential을 제시하면 제어 요청은 거절한다. 결과·정리 기록은 남으며 새 세션이 과거 실행을 자동 인수하거나 다시 시작하지 않는다.
6. credential을 로그·감사 detail·MCP 도구 응답·증거·보고서·커밋에 넣지 않는다. handoff 시 대상의 공개 ownerId만 사용한다. 사람 CLI·GUI 경로와 agent 경로의 구분을 유지한다.

IPC의 v1 `hello`와 `accepted`는 현재 strict schema이므로 여기에 무조건 추가 필드를 보내면 기존 클라이언트가 깨진다. 기존 프레임은 유지하고 지원 협상 후 요청하는 opt-in auth 필드로 credential을 전달하는 안을 제안한다. 새 auth 필드는 HMAC의 nonce·방향·역할과 함께 결합하고, 검증 실패 시 내부 요청 처리 전에 거절한다. capability가 없는 old service에는 그 필드나 새 명령을 보내지 않는다. 정확한 내부 frame·CallerContext 타입은 총괄 공통 계약 확정 사항이다.

### 사람의 명시적 인계.

`handoff-run`을 human-only API 및 CLI/GUI 동작으로 제안한다. 입력은 runId, 기대한 기존 ownerId 또는 ownership revision, 대상의 현재 epoch ownerId, confirm, 근거 note다. 서비스는 대상의 실제 등록, 실행 상태와 소유권 revision을 검사하고 원자적으로 제어 소유자를 바꾼 뒤 감사 기록을 남긴다. 대상 credential을 화면에 입력·복사하지 않는다.

인계는 동시 수행 중 run·plan·workspace·dataRoot·정리 상태를 사람에게 보여 준다. 인계 이후 이전 A의 cancel과 제어 요청은 거절하고 B만 새 제어권을 가진다. 이미 접수된 큐 항목의 preflight는 현재 owner 기록과 현재 epoch의 유효 주체를 확인하므로 명시적 인계만으로 정상 큐를 취소하지 않는다. 인계 자체는 approve·cleanup·unknown 해소·새 실행을 수행하지 않는다. 재시작 뒤 unknown 실행의 인계도 결과를 재실행하지 않으며 상태상 불가능한 cancel은 그대로 거절한다.

이는 같은 OS 사용자의 셸·dataRoot 비밀에 접근 가능한 악성 코드 전체를 격리하는 보안 장치가 아니다. 현재 trust와 human 역할 경계도 그 권한을 가진 셸을 인증된 사람으로 증명하지는 않는다. 이번 범위는 정규 MCP 클라이언트 사이의 제어 혼선을 막는 로컬 권한 계약이다.

## 4. 공유 자원 잠금과 안전한 대기.

- 기존 workspace 배타 접수와 최대 두 실행 큐를 유지한다. 같은 workspace 또는 공유 자원 충돌은 fail-fast로 거절한다. 전역 자원 경합을 위한 새 자동 대기·재요청 기능은 만들지 않는다.
- 선택 명령의 `writes`는 현재 프로젝트 상대 경로다. workspace의 실제 경로와 합쳐 정규화하고 디렉터리 조상·자손 겹침도 충돌로 본다. 미생성 경로는 가장 가까운 실제 부모를 확인하며 링크·정션·경로 이탈은 거절한다. `cache`와 `cache/sub`를 별개 락으로 허용하지 않는다.
- 별도 명시 공유 자원은 command의 선택 `exclusiveResources` 배열로 제안한다. 비밀이나 임의 SQL 대신 사람이 정한 비민감 공유 키를 쓰며 등록 카탈로그·지문·승인에 포함한다. 예를 들어 같은 엔진의 두 명령에 같은 포트·출력·공유 fixture를 가리키는 동일 키를 지정한다. 키 alias 자동 추론이나 외부 시스템 전역 탐지는 하지 않는다.
- 같은 호스트 사용자 아래 여러 dataRoot가 합의한 공통 `lockRoot`를 사용한다. 기본 위치 제안은 `%LOCALAPPDATA%/CheckMateLocks`이며 별도 합성 시험은 자기 전용 lockRoot를 명시한다. 총괄이 경로·권한·링크 거부·옵션 전달 계약을 확정한다. capabilities에 실제 lockRoot 또는 일치 확인용 식별자를 제공해 보호 범위를 확인한다.
- 파일 잠금과 서로 다른 SQLite 파일을 하나의 DB 트랜잭션으로 원자화할 수는 없다. 먼저 정규화·중복 제거·정렬한 전체 락 집합을 준비한다. 공통 lockRoot의 짧은 배타 registry guard 아래 전체 집합 충돌을 확인하고, runId·owner·dataRoot 지문·request hash·전체 키·단계를 담은 intent lease 하나를 배타 생성·fsync한다. 한 실행의 전체 집합을 모두 취득하거나 전부 실패하며 부분 점유 대기는 하지 않는다. path 충돌은 lease의 정규 경로와 조상·자손을 비교한다. 여러 파일을 쓰는 구현을 선택하면 항상 같은 순서로 획득하고 실패 때 자기 generation의 확인된 획득분만 반환한다.
- 다음으로 해당 dataRoot의 DB 트랜잭션에서 run·owner·request·lease 참조를 함께 접수한다. 그 뒤 lease를 admitted로 내구성 기록하고 실행 큐에 넣는다. 파일락→DB 원자 접수→lease 확인→executor 순서를 지키며 파일과 DB 전체가 원자적이라고 표시하지 않는다.
- 기존 동일 요청 재확인 때 새 lease를 만들지 않고 기록된 동일 run·lease로 연결한다. 락 취득 후 DB 접수 전 충돌·완전 rollback·미착수 여부를 긍정적으로 확인한 경우만 자기 lease를 해제한다. 접수 응답 유실·DB 확정 불명·admitted 표식 기록 실패면 lease를 보존하고 재조회한다. registry guard 자체의 crash·소유 불명도 fail-closed로 남기며 시간만으로 지우지 않는다.
- 접수 직전 source 검증 후 DB 트랜잭션에서 활성 카탈로그·승인과 자기 lease 연결을 다시 확인한다. 경로와 source 및 실제 공통 lease는 실행 직전에도 재확인한다. 외부 잠금 구현은 소유자·generation 비교 없이 다른 세션 파일을 지우지 않는다. 선언하지 않은 OS 외부 부작용까지 자동 감지·차단한다고 주장하지 않는다.
- RunService가 기존 큐에서 executor를 호출하기 바로 전에 ProductService의 preflight를 await한다. 현재 plan/workspace/catalog/approval/sourceHash, 유효한 현재 제어 소유자, 전체 락이 해당 run에 계속 귀속되는지를 확인한다. 실패하면 명령 spawn과 자원 prepare 없이 blocked로 확정한다.
- 실제 시작 전 차단·큐 취소는 자원 준비가 없음을 확인한 경우에만 락을 해제한다. 이미 prepare/spawn을 시도한 실행은 프로세스와 자원 정리 확인을 모두 요구한다. 단순 최종 상태·PID 부재·소켓 종료는 해제 조건이 아니다.
- `cleanupVerified !== true`, 저장 확정 실패, 종료 불명, 복구 중 running→unverifiable이면 락을 보존한다. 시간 만료나 서버 재시작으로 해제하지 않는다. 사람 전용 자원 정리와 acknowledge-cleanup의 실제 범위 확인 뒤 락 해소 감사만 추가하고 과거 판정은 유지한다.
- Docker/native가 실행별 동적 포트·전용 자료 폴더를 만드는 경우 PostgreSQL 종류 자체를 전역 락으로 직렬화하지 않는다. 독립 자원은 기존 두 실행 한도 안에서 병렬 실행할 수 있다.
- 이번 공유 락의 보호 범위는 같은 호스트 사용자와 같은 공통 lockRoot를 사용하는 엔진들이다. 서로 다른 dataRoot도 같은 선언 키·실제 writes가 겹치면 보호한다. 다른 lockRoot·OS 사용자·호스트·원격 DB 전체의 전역 보호는 보장하지 않는다. 기존 클라이언트가 이 계약을 지원하지 않으면 새 MCP 제어를 안전하게 제한한다.

## 5. 중복 요청·응답 유실·재시작.

새 제어 주체의 requestId는 같은 서비스에서 workspace를 바꿔도 재사용 충돌을 찾아야 한다. `(ownerId, requestId)`와 정규화한 의미 본문 hash를 별도 기록하는 안을 제안한다. 본문은 method, projectId, 저장 계획의 workspaceId, planId를 포함하고 plan fingerprint와 연결한다. 동일 의미의 workspaceId 생략·명시는 정규화해 비교하며 다른 plan·workspace·본문은 `request-conflict`다. 서로 다른 정상 owner의 requestId 우연 중복은 제어권 공유로 이어지지 않는다.

기존 `(workspace_id, request_id)` 자료와 hash 알고리즘은 유지한다. legacy 요청을 새 owner가 주장해 제어권을 얻지 않게 한다. 사람 CLI의 기존 request 재확인 호환은 별도로 보존하며 새 저장 형식 때문에 과거 실행을 복제하지 않는다.

응답 유실 때 MCP는 원래 body와 requestId를 보존한다. 명시적으로 같은 요청을 재확인하면 같은 runId를 반환하고 큐·executor·자원 생성은 추가하지 않는다. 발견한 실행이 finalized/unknown이어도 같은 실행을 반환한다. 새로운 requestId로 자동 재요청하지 않는다. 다른 owner의 동일 request 조회가 제어권을 만들지 않는다.

서버 재시작은 기존 queued/running 복구와 요청 자료를 유지하고 새 credential로 과거 요청을 자동 재실행하지 않는다. 과거 실행은 runId·이력으로 읽기 조회한다. 이전 credential 또는 ownerId만으로 start/cancel/handoff가 성공해서는 안 된다. 저장되지 않은 접수인지 확인할 수 없으면 unknown으로 안내하며 새 실행을 만드는 자동 복구는 금지한다.

## 6. 기존 v1 저장 자료와 클라이언트 이행 제안.

총괄에 다음 추가 스키마와 이행기를 요청한다. 기존 v1 SQL·checksum·결과 JSON·실행 ID를 조용히 바꾸거나 자동 reset하지 않는다.

| 제안 저장 범위 | 내용·영향 |
| --- | --- |
| workspace_catalog_state | workspaceId별 활성 catalogId를 보관하고 같은 project에 속하는지 FK 또는 trigger로 확인한다. 기존 단일 폴더의 project 활성 포인터를 복사한다. |
| run_control_owners | runId별 공개 ownerId, owner proof hash, serviceEpoch, ownership revision을 보관한다. 이전 실행은 legacy/unclaimed로 남기며 agent에게 임의 귀속하지 않는다. credential 원문을 저장하지 않으며 hash만으로 재시작 인증을 허용하지 않는다. |
| owner_requests | ownerId/requestId/의미 hash/runId/workspaceId를 보관한다. 기존 requests는 별도 보존한다. |
| execution_locks | runId별 공통 파일 lease 참조와 workspace·path·named-resource 락 집합·보존 상태를 보관한다. DB 접수와 참조 기록은 원자적이며 파일 취득과 DB 사이의 불명 상태는 보존한다. unknown에 타임아웃 해제를 적용하지 않는다. |
| audit_events | 기존 테이블로 제어 인계·이행·락 해소 근거를 기록한다. secret·실제 고객 자료는 기록하지 않는다. |

현재 `connectStore`는 migration이 정확히 한 행인 경우만, 백업은 현 schemaVersion/checksum/table 집합만 허용한다. 따라서 version 숫자 변경만으로 이행을 구현할 수 없다. 총괄이 [저장 연결](../packages/engine/src/저장/연결.ts), [스키마](../packages/engine/src/저장/스키마.ts), [백업](../packages/engine/src/저장/백업.ts)의 v1 검증·명시 이행·이행 뒤 재검증·기존 백업 읽기를 함께 설계한다.

이행 전 유휴와 실제 기존 서비스 소유권, 백업·디스크 상태를 확인한다. 승인된 합성 v1 사본으로 시험하고 기존 운영 저장 파일은 이 Task에서 열거나 적용하지 않는다. v1 실행·계획·승인·증거·공백·가져온 이력의 지문과 ID를 보존한다. queued/running 또는 정리 미확인 자료는 실행·자원 보유 가능성을 유지하고 이행만으로 해제하지 않는다. 새 원본 계약의 선택 필드를 지문에 포함하면서 기존 plan JSON을 재해석해 승인 범위를 넓히지 않는다.

| 서비스·클라이언트 조합 | 최소 동작 |
| --- | --- |
| 새 MCP·새 서비스 | workspace 기능과 제어 capability를 확인하고 내부 credential을 연결한 뒤 안전한 start/cancel을 제공한다. |
| 구 MCP·새 서비스 | 기존 읽기 도구는 유지한다. 신뢰할 제어 맥락 없는 start/cancel은 `service-update-required` 또는 `agent-control-required`로 거절한다. inspect/sync도 단일 workspace 또는 명시 가능한 범위만 허용한다. |
| 새 MCP·구 서비스 | 기존 조회는 유지하며 다중 workspace·제어 보호가 없으면 MCP start/cancel을 기능 부족으로 제한한다. 보호 기능을 있는 것처럼 채워 넣지 않는다. |
| 사람 CLI·GUI | 단일 workspace 기존 인자는 유지한다. 다중 workspace에는 명시 선택을 요구하고 human-only 승인·인계를 별도 표시한다. 구 GUI의 projectId만 요청은 다중 대상에서 `workspace-required`로 거절한다. |
| 구 실행기·새 저장 스키마 | 기존 실행기를 강제 종료·업데이트하지 않는다. 구 실행기의 명확한 지원 버전 오류를 유지하고 원본 v1 백업을 보존한다. |

모든 조합에서 API의 새 필드는 capability 확인 후 보낸다. 기존 v1 MCP 도구 이름과 stdio stdout 규칙, 8KiB/32KiB 응답 한도, 실패/미실행/unknown 판정은 유지한다. 내부 세션 발급·인계·approve·cleanup을 새 MCP 공개 도구로 노출하지 않는다.

## 8. PG/Docker·wrapper 팀에 요청할 선행 계약.

- 제공자 모드는 사람이 검토할 계획에 `docker/native`로 명시한다. 기존 명령은 docker 기본값을 보존한다. native 불가·시작 실패를 Docker fallback으로 숨기지 않는다.
- 제공자 경계는 기존 `prepare(runId, ownerToken, signal, resourceKinds)`와 `cleanup(runId)`의 환경·비밀·정리 결과 형태를 재사용하되 모드 선택을 불변 계획에서 전달한다. 정확한 옵션 타입은 총괄 `시험자원.ts/프로젝트.ts` 계약으로 확정한다.
- prepare는 생성 전에 intent를 내구성 있게 기록하고 실행별 전용 자료·포트·정확한 소유 식별자를 연결한다. cleanup은 해당 자원만 종료·제거하며 unverifiable 상태를 cleaned로 바꾸지 않는다. 신규 자원 state/schema 변경은 총괄이 소유한다.
- preflight는 W2 `ProductService→RunService` 경계에서 먼저 끝나야 한다. 후속 워커2 executor는 기존 원본·명령 검사를 유지하고 prepare를 그 뒤 수행한다. 코어와 provider 담당이 동시에 executor/ProductService를 편집하지 않는다. ProductService의 capability 최소 변경만 코어 정산 뒤 승인된 전체파일 순차 인계로 처리한다.
- resource mode·실행 파일·자료 위치·쓰기와 삭제 범위·고정 공유 자원이 달라지면 source/catalog/plan/approval 지문에 반영한다. native의 저장 위치·owner 기록 변경이 필요한 경우 총괄 schema 변경과 함께 직렬 처리한다.
- GUI 자원 안내의 `시험자원.tsx`와 workspace 선택·인계의 `앱.tsx`는 현재 실제 W2 Task 소유다. PG 팀은 제공자 안내·효과를 해당 소유자에게 계약으로 전달하며 승인 없이 파일을 이전하지 않는다. 후속 담당 변경이 필요하면 고정 후보 인수와 총괄 명시 인계 뒤 처리한다. 새 공통 타입·제공자 구성 주입은 총괄 확정 뒤 각 소유자가 적용한다.
- 선택 wrapper는 사람이 등록한 Node entry/args/checkIds만 실행한다. 임의 셸·SQL·경로 도구를 추가하지 않는다. 실제 아틀리에 wrapper 변경은 다른 프로젝트 담당의 별도 Task다.

### 10.1. 제공자와 실행기 인터페이스.

현재 command의 `resources?: DatabaseResourceKind[]`와 `DatabaseResources.prepare(runId, ownerToken, signal, kinds)`의 `{ environment, secrets }`, `cleanup(runId)`의 `{ verified, resources }` 결과는 재사용한다. `검사실행기.ts`의 `Options.resources`가 이미 prepare/cleanup만 요구하므로 불필요한 새 실행 서비스 계층을 만들지 않는다.

총괄 `msg_11e72f8c2ea4`를 반장 `msg_abdf5ad386df`로 수신한 확정 계약은 command catalog의 optional `resourceProvider` strict DTO다. 이전 문자열 mode 선택과 실행 뒤 binaryRoot 주입 제안은 이 계약으로 대체한다. 생략 또는 명시 Docker DTO는 기존 Docker 기본값이다. native DTO는 `mode: 'native'`, 절대 실제 `binaryRoot`, `postgresVersion`, `initdb`·`pg_ctl`·`postgres` 각각의 SHA256을 동결한다. native는 `postgres-test`만 허용하며 실행 내 서로 다른 native 구성이나 Docker/native 혼합은 inspect 단계에서 거절한다. native 불가·시작 실패를 Docker fallback으로 바꾸지 않는다. 구 서비스에는 capability 없이 새 필드를 보내지 않는다.

adapter signature 후보는 `prepare(runId, ownerToken, signal, kinds, frozenProvider?)`다. 마지막 인자는 등록/activate/inspect와 사람 승인에서 고정된 strict DTO만 executor가 원본 지문 재검증 뒤 전달하며 기존 네 인자 호출은 Docker를 유지한다. `FixedCommand`가 그 DTO를 보존하고 executor가 서로 다른 구성/혼합을 재확인한다. MCP start 입력은 해당 구성 또는 binaryRoot/hash를 덮어쓰지 못한다. cleanup은 현재 설정이나 입력 mode가 아니라 저장된 descriptor의 provider와 binary fingerprint를 사용한다. 작업에 전달하는 PG 환경 및 비밀 가림은 기존 `databaseConnection`·`selectDatabaseEnvironment`를 재사용한다.

binaryRoot는 사람이 등록한 command catalog의 실제 구성만 허용한다. 임의 PATH/환경 탐색·다운로드·사용자 DB 연결은 추가하지 않는다. 총괄이 읽기 확인한 `C:/Users/ADMIN/AppData/Local/AtelierNote/PostgreSQL17/pgsql/bin`의 PostgreSQL17.11을 읽기 재사용할 수 있으나 기존 Atelier cluster에 접속하지 않는다. binary 위치와 세 파일 fingerprint/관측 version, provider mode, 새 엔진 전용 resourceRoot와 정확한 자원 생성/쓰기/정리 효과는 사람이 검토하는 불변 계획과 승인 지문에 연결해야 한다. 계획 때 고정한 실제 path/version/SHA를 prepare 및 cleanup 직전에 다시 검증하고 바뀌면 새 binary로 실행/정리를 대신하지 않는다. 준비 전 불일치는 착수 거절이고 이미 생성된 자원의 정리 전 불일치는 uncertain과 자료·락 보존이다. 이 때문에 공통 계약과 서비스 구성 주입 파일의 명시 인계가 선행한다.

### 10.2. 자원 저장과 native 정리.

현재 `ResourceStore`의 strict Docker descriptor는 `name/image/endpoint/daemonId/containerId/hostPort`이며 intent·update·cleaned 조건도 Docker ID를 전제로 한다. enum에 native만 추가해서 처리하지 않는다. 기존 descriptor JSON을 그대로 허용하는 legacy Docker branch와 새 명시 native/version branch의 strict union을 제안한다. 기존 record에 provider를 주입하거나 다시 저장하지 않는다.

native branch는 run/resource 식별자와 전용 cluster 실제 경로·marker fingerprint, 등록된 binary 경로/버전/fingerprint를 불변 소유 정보로 기록한다. PID·프로세스 시작 식별자·loopback port는 실제 관측 후에만 채우며 기존값 교체를 허용하지 않는다. native intent/update/cleaned의 조건을 별도로 검증하고 Docker branch의 기존 회귀를 유지한다. `descriptor_json`으로 수용할 수 있으면 SQL 이행은 추가하지 않는다. 열·상태·version 변경이 필요하면 총괄에 정확한 schema 이행을 먼저 요청하며 v1 SQL/checksum은 바꾸지 않는다.

initdb 전에 intent를 기록하고 CheckMate 전용 새 빈 자원 폴더와 marker를 준비한다. 자료 폴더는 실제 격리 resourceRoot의 run/resource 하위이고 기존 cluster를 대상으로 하지 않는다. loopback의 실행별 임시 port를 사용하며 독립 native PG 두 자원을 PostgreSQL 종류 전체 락으로 직렬화하지 않는다. 포트 충돌은 준비 실패이며 기존 서버에 대신 접속하지 않는다.

shutdown/delete는 저장된 정확한 실제 path·marker·실행 파일·프로세스 소유 관측이 일치할 때만 가능하다. PID 파일·pg_ctl 종료값 하나로 검증 완료를 결정하지 않는다. 프로세스 종료/포트 해제/전용 자료 정리의 긍정 근거가 없으면 uncertain과 자료·공유 락을 보존한다. 서비스 재시작·시간 만료·사람 실행 인계는 자동 자원 정리 권한이 아니다. 현재 OS 사용자 셸 권한 전체를 격리하는 보안이라고 설명하지 않는다.
